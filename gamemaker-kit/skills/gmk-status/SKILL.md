# gmk-status — Where am I, what's blocked, what's next

This skill exists to answer one question:

> *"If I sat down in front of this project right now, what's the **one** thing I should do?"*

It does **not** restate the project plan. It looks at current state across four axes (pillars, milestones, per-discipline tasks, validation) and surfaces the bottleneck — the thing that, if unblocked, frees the most other work.

The model was haiku in v0.1 (read-only tree). It's now **sonnet** because bottleneck detection requires understanding cross-discipline blockers and reasoning about which next action has the highest leverage.

## Two outputs, one source of truth

1. **`_workspace/dashboard.md`** — written every run (overwrites). The user opens this in VSCode between sessions; it's their home screen.
2. **Chat tree** — printed during the call. Same content, terminal-shaped. The user can grep / scroll.

Canonical state lives in `pillars.json` + `milestones.json`. Dashboard is a **rendered view**, not a separate source. Anyone who hand-edits `dashboard.md` will get overwritten — there's a warning at the top.

## Preconditions

1. **Inside a gamemaker-kit project** — `.gamemaker-kit/` exists.
   - Missing: *"No `.gamemaker-kit/` here. Either you're in the wrong directory, or you haven't run `/gmk-init` yet."*
2. **`pillars.json` exists.** Even if `skipped: true` — that's still a valid state.
3. **`milestones.json` exists.** If missing, treat as `{ milestones: [] }`.
4. **`_workspace/` exists.** Create if missing (we're about to write `dashboard.md` there).

Do not refuse on malformed JSON. Print the parse error and the file path, then stop. Repair is a separate concern — gmk-status is not a fixer.

## Flow

### Step 1 — Read state

Read `pillars.json` and `milestones.json`. Compute these derived facts (don't print them yet):

| Derived fact | How to compute |
|---|---|
| `active_milestones` | Milestones where `killed !== true` AND `validation?.verdict !== 'PASS'` OR `ported_to == null` |
| `shipped_milestones` | `killed !== true` AND `validation.verdict === 'PASS'` AND `self_test?.latest_verdict === 'PASS'` AND `ported_to?.re_validation?.verdict === 'RE_PASS'` |
| `killed_milestones` | `killed === true` |
| `blocked_tasks` | Across all active milestones, `tasks[].status === 'blocked'` |
| `oldest_block_age_days` | Max age (now − `updated_at`) across `blocked_tasks` |
| `pillar_coverage` | For each pillar, count active milestones targeting it |
| `pillars_with_zero_coverage` | Pillars with 0 active milestones |
| `pending_self_tests` | Milestones with `validation.verdict === 'PASS'` but no `self_test` entry (or stale) |

### Step 2 — Pick the *one* recommended next action

Run this priority ladder. **Stop at the first match.**

1. **Crash-level milestone** — any milestone with `validation.metrics.crash_rate >= 0.5`. The prototype is broken; nothing else matters until that's fixed.
2. **Blocked task aging > 3 days** — name the task and what's blocking it. Aging blockers eat morale; clearing them takes hours, while waiting for them takes days.
3. **Pending self-test on a PASS milestone** — bot says PASS but user hasn't played it. Faster to play 20 minutes than to start new milestone work.
4. **Pillar with zero coverage** — surface it; suggest `/gmk-roadmap` or `/gmk-brainstorm`.
5. **Active milestone with no prototype yet** — earliest one in roadmap order; suggest `/gmk-prototype <id>`.
6. **Active milestone with FAIL** — suggest `/gmk-kill-milestone` decision or hypothesis revision.
7. **In-progress task with no recent update** — name the task (status `in-progress`, `updated_at` > 5 days ago).
8. **All milestones shipped (no in-flight, no killed pending)** — *"All milestones shipped. Run /gmk-dev-complete to check the project-level endpoint (pillar coverage + warnings)."*
9. **Default** — *"Multiple milestones in flight — pick whichever feels most alive to you today. Status is healthy."*

**Only ever surface one.** If the user wants more, they can read the tree.


### Step 5 — That's it

Don't auto-run anything else. Don't suggest `/gmk-validate` or `/gmk-prototype` unless they're the recommended next action. The dashboard is a window, not a launcher.

## Status markers (closed set)

| Marker | Meaning |
|---|---|
| `✓` | PASS / Done |
| `✗` | FAIL |
| `⏳` | Pending / INCONCLUSIVE |
| `🚧` | In progress |
| `🚫` | Blocked |
| `📋` | Backlog |
| `👁` | Review |
| `⚠` | Warning (e.g., pillar gap, drift, scope concern) |

Don't invent new markers mid-tree.

## Edge cases & policy

### Killed milestones in the bottleneck calculation

**Excluded.** Killed milestones don't have blockers worth surfacing. They appear in the learning trace section but don't affect the recommendation.

### Pillars skipped at init (`pillars: []`, `skipped: true`)

Show a warning banner above the tree:

```
⚠ Pillars were skipped at /gmk-init. Without them, milestones have no north star —
  every "did it work" question is context-free. Worth ten minutes to run /gmk-init properly.
```

Then print the tree (without pillar coverage section).

### Drift detection — pillar added after milestones exist

If any pillar's `created_at` (if tracked) is **after** the most recent milestone's `created_at`, flag at the top:

```
⚠ Pillar drift: pillar 'greed-vs-safety' added 2026-05-11, after milestones m1/m2 existed.
  Existing milestones don't target it. Run /gmk-roadmap to plan new milestones for the new pillar.
```

If pillar created_at isn't tracked, skip this check silently.

### Re-validated milestones (multiple bot runs)

Show the count: `bot: ✓ PASS (3 trials, latest 200 runs)`.

### Forced ports (`ported_to.forced === true`)

Show a warning: `port: ✓ RE_PASS (FORCED — bot or self-test gate did not pass at port time)`. Audit the user's earlier decision; surface, don't hide.

### Empty project (no milestones, just pillars)

```
{project}   (3 pillars, 0 milestones)

Pillars: (all locked, no coverage)
  ⚠ tactile-satisfaction
  ⚠ discovery-joy
  ⚠ greed-vs-safety

Suggested next: /gmk-roadmap  — break the pillars into 3-8 milestones with priorities.
```

### Tasks not yet split for an active milestone

If a milestone has `prototype !== null` but `tasks` is missing/empty, surface in the bottleneck calc as a candidate — *"m2 has a prototype but no task list; run /gmk-task-split to make per-discipline progress visible."*

### Milestone in `_workspace/milestones/<id>/notes.md` but not milestones.json

Don't silently fold those in. The notes file is user-owned scratch space; if there's a milestone idea there that hasn't made it to canonical state, gmk-status doesn't know about it. The user can move it themselves via `/gmk-roadmap`.

### Stale `in-progress` task (no updates for 5+ days)

Surface as: `t-m2-code-counter — 🚧 in-progress (no update 7 days)`. Don't auto-transition. The user might be away; the kit doesn't second-guess.

## What this skill does NOT do

- **Doesn't modify canonical state.** Read-only on `pillars.json` and `milestones.json`. The only write is `_workspace/dashboard.md`.
- **Doesn't run other skills.** Status is a window. The user runs the next action themselves.
- **Doesn't ping URLs, services, or external systems.** No GitHub, no itch.io, no Discord. The kit's contract: zero external dependencies for status.
- **Doesn't auto-transition task statuses.** Stale tasks are surfaced, not advanced.
- **Doesn't editorialize.** *"This milestone is exciting"*, *"that one's a slog"* — no. Just the data and the one recommended action.
- **Doesn't recompute validation.** If `validation.verdict === 'PASS'` is stored, the kit trusts it. Re-running validation is `/gmk-validate`'s job.
- **Doesn't replace `/gmk-roadmap` or `/gmk-task-split`.** Those write canonical state; this skill renders.

## Notes for the model running this skill

- **Bottleneck > status.** The chat tree is 80% of the output, but the *recommendation* is 80% of the value. Don't bury it in a wall of text.
- **One screen.** The chat tree should fit on a 60-row terminal for a typical project. If the user has 20 milestones, the tree compresses (one-line summary per shipped milestone, full detail only on active).
- **Don't lecture on failed milestones.** If m2 is FAIL, the tree shows it; the user doesn't need a paragraph on why FAIL means kill-or-revise. They know.
- **Aging matters.** A blocker that's 1 day old is a blip; 5 days is a project problem. The recommendation should weight blocker age heavily.
- **Don't suggest things outside gmk's scope.** No "consider posting on Discord for feedback." No "set up a Steam page." Recommendations are for gmk-skill next actions only.
- **Self-test pending is a high-priority bottleneck.** A PASS bot + no self-test means a real human session is the cheapest unlock. 20 minutes of play > 2 days of new prototype work.
- **Markdown emoji rendering varies.** The status markers (`✓`, `✗`, etc.) are plain Unicode; the emojis (`🚧`, `🚫`) are for dashboard.md (VSCode renders them well). In the chat tree, use ASCII fallbacks if the terminal looks suspect.
- **The recommendation has to *name* the bottleneck — not just point at it.** Bad: "Look at the blocked task." Good: "t-m2-audio-thud has been blocked on t-m2-art-particles for 3 days. Unblock art and audio flows again."

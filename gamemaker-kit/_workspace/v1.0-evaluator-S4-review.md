### Major

So: if module-build Step 5 already wrote `confirmed:true`, invoking gmk-confirm and leaving it pending does not lower `confirmed`; gmk-port still passes. The plan justifies the block via `confirm.confirmed` but implements via `confirm.status`; nobody reads status. **Fix**: gmk-confirm Step 3, on creating a pending visual confirm, must set `confirm.confirmed = false (or null)` as the authoritative downgrade the moment it takes the field with `method:"visual"` — then the existing gmk-port gate genuinely blocks. `status` can stay as a human resume hint, but the load-bearing gate must ride `confirm.confirmed`.

**M2 — module-build/gmk-confirm authority handoff has an unspecified ordering hazard.** (§3, §0 item 3) Both write the same `confirm` field at independent times. Reverse order is destructive: gmk-confirm runs (writes method:visual/confirm_html/confirmed_at), then user re-runs module-build after a fidelity miss → its Step 5 overwrites the entire confirm object back to method-less text shape, silently discarding gmk-confirm's fields. "gmk-confirm overwrites authoritatively" is only true until the next module-build clobbers it back. Since §3 says module-build is NOT edited, this is a genuine last-writer-wins collision the plan must acknowledge (e.g. "re-running module-build resets confirm to text; user must re-run gmk-confirm").

## §1 — Dogfood project design

**Recommendation: a single small grid-shape merge-or-puzzle game with 3 pillars and 2 milestones, living outside the kit repo.**

Specifics below.

### 1a — Mechanic class / shape coverage

**Pick one shape, not all four. Specifically: `grid`.**

The argument for "test all 4 shapes in one dogfood" is wrong. Reasons:

1. **The kit's own scope check forbids it.** `gmk-init:91-96` and `gmk-shape-advisor:60-62` both call out that `dialogue` is "rare for the kit's typical user — if the user's pillar is *tactile satisfaction* or *greed vs safety*, it's almost certainly not dialogue", and `shape-advisor:55-57, 197-198` says shader is for pure-visual milestones with no play loop. Forcing one project to legitimately exercise all 4 shapes means designing a project that *violates* the kit's own genre advice. That isn't dogfood; it's a synthetic 4-shape sweep.
2. **Per `shape-advisor:255-256`, "shape disagreement between milestones in the same project is allowed and normal."** Multi-shape coverage is a property the kit explicitly leaves to *the corpus across projects*, not to one project.
3. **`grid` is where the bot validator is strongest** (`shape-advisor:21` — random/MCTS/persona-mix all fit; `gmk-validate:68` notes dialogue is INCONCLUSIVE-by-design). If the v0.10 dogfood's purpose is to test the *bot validation chain* end-to-end, you want the shape where the chain has the most to say. A dialogue dogfood would terminate at "INCONCLUSIVE" and prove nothing about whether `gmk-validate → gmk-self-test → gmk-port` actually works for the kit's *core* user.
4. The other 3 shapes can be covered later by **separate small dogfoods, one per shape**, post-v1.0. Treat them as "shape conformance tests" not v1.0 gates.

**Mechanic: a 3×3 or 4×4 merge-pair board where same-tier adjacent items merge to next-tier, with a small "greed vs safety" tension (e.g., merging consumes the slot, board-full = game over).** This is the smallest mechanic that exercises `legalActions()` non-trivially, has a real `isOver()`, a real `score` (tier-sum or merge-count), and a state-coverage signal worth `stateSignature()` (board hash). It is *not* ZooMerge — it should be deliberately smaller and named separately so it cannot be mistaken for the real game.

Working name suggestion: `gmk-dogfood-merge3` or similar; the actual name is the user's call.

### 1b — Pillar stress design

**Stress test, but lightly. Specifically: 3 pillars, one of each shape — sensory, behavioral, decision-shape. Skip `emotional`.**

- **Why include 3 shapes**: this exercises Rule 17 routing meaningfully. `gmk-init:188` writes `kind` per pillar; `prototype-rules` Rule 17 routes downstream metrics/agents based on it. If all 3 pillars are the same shape, Rule 17's routing table never branches and the test is degenerate.
- **Why skip `emotional`**: per `gmk-init:22-23` and the user's own pillar-framing memory (`feedback_pillar_framing.md` — "감정만 강요 금지"), `emotional` is the squishiest shape and is the one the kit explicitly tells users to drop in favor of behavioral/decision-shape if there's any resistance. A dogfood pillar set should reflect the kit's *recommended* mode, not its softest one. If you want to additionally test the emotional path, do it in a second dogfood — don't conflate them.
- **Stress idea (light)**: make one pillar deliberately almost-ambiguous to test Rule 17's "pick dominant shape, note ambiguity" handling at `gmk-init:188`. Example: a pillar called *"Satisfying chain merges"* that could read as `sensory` (the chunkiness of the chain animation) or `behavioral` (the player keeps reaching for longer chains). Classify it as `behavioral` per the rule, note the ambiguity in the description. If the kit handles it cleanly, that's a real positive signal; if downstream skills produce confusing output, that's exactly the kind of v0.10 defect this whole exercise is meant to surface.

**Do not deliberately design pillars to *fail* the kit.** Adversarial pillars are not dogfood — they're property testing. The point of dogfood is "what does a real reasonable user hit?", and a real reasonable user picks the kit's recommended modes.

### 1c — Minimum milestone count

**2 milestones, with `gmk-mechanic-merge` between them on a 3rd integration milestone (so really 2 + 1).**

This is the smallest configuration that exercises the *full* path:

| Milestone | Purpose | Path exercised |
|---|---|---|
| `m1-merge-basic` | Core merge mechanic (`grid` shape). | `gmk-init → gmk-roadmap → gmk-shape-advisor → gmk-prototype → gmk-validate (PASS) → gmk-self-test (PASS) → gmk-port (RE_PASS)` |
| `m2-greed-tension` | Add board-full lose condition + score target. | Same chain, *plus* `gmk-regression` (because m1 is now a prior PASS) *plus* `gmk-merge-gate` (because m2 touches the shared merge code from m1) |
| `m3-merge-integration` (optional but recommended) | `/gmk-mechanic-merge` of m1 + m2 (post-validation merge of the two mechanics into a single integrated playable). | `gmk-mechanic-merge` itself |

This hits every load-bearing skill in the kit's core path (16 skills) without needing the optional ones (`gmk-narrative`, `gmk-save-migrate`, `gmk-art-gen` — your report's §3.4 already flagged these as narrow-scenario). If even *2 milestones* turns out to be too much for one author-session, drop to 1 milestone + skip the merge-gate path — but then call it explicitly in the dogfood report ("merge-gate path not exercised in v0.10; v1.0.1 needed").

The Critical-blocker test (from the v0.9 verdict) only requires *one* milestone reaching RE_PASS. The 2-milestone version is what lets the kit say "yes, the inter-milestone interactions work too" — which is materially stronger evidence and the difference between v1.0 and a wobbly v1.0.

### 1d — Filesystem location

**Outside the kit repo. Recommendation: `C:\GameMaking\Godot\gmk-dogfood-merge3\` (or whatever the actual project name resolves to).**

Reasons:

1. The kit `gmk-init:143-153` writes `prototypes/`, `.gamemaker-kit/`, and `_workspace/` *inside the project root*. If the dogfood lives inside `gamemaker-kit/`, you get `gamemaker-kit/prototypes/`, `gamemaker-kit/.gamemaker-kit/`, `gamemaker-kit/_workspace/<dogfood-files>` — three directories that *also exist in the kit itself*, with different semantics. That's a real footgun (e.g., `gamemaker-kit/_workspace/` already holds the v0.9-*.md meta-artifacts).
2. The kit ships with `templates/`, `skills/`, `scripts/`, `README.md`, etc. Polluting that repo with a working game's commits would conflate "kit changes" with "game changes" in the git log — exactly what `pathspec_explicit_add` memory warns about for a different reason (additive pathspec footgun on commits).
3. Tight coupling argument: the dogfood *should* be loose-coupled to the kit. The whole point is that the kit is installed as a plugin (`README.md:14-16` — `/plugin install gamemaker-kit`) and used from any project root. If the dogfood requires sitting inside the kit repo, that's evidence of an integration defect, not a feature.
4. The user's memory `project_gmk_dogfood_separate.md` already documents that the dogfood is a separate game from ZooMerge — the same separation-of-concerns argument applies to physical location.

**Tradeoff with "tight coupling"**: there is none. The kit reads no files from its own repo when running on a user project — it reads `pillars.json`, `milestones.json`, `prototypes/*.html` from the *user's* project. The kit-skill files are read by Claude Code's plugin system, not by other kit files. So putting the dogfood elsewhere costs nothing operationally.

**Engine choice**: pick `godot`. `gmk-init:109-112` already recommends Godot as default; `gmk-port:32-38` only auto-generates code for Godot (Unity is "Phase 2 — checklist only"). A Godot dogfood actually exercises Stage 1 code generation; a Unity dogfood would stop at Stage 1 and you'd never see Stages 2-5 fire. That defeats the purpose.

## §2 — QUICKSTART structure

**Recommendation: a verbatim transcript of the v0.10 dogfood *first session* (gmk-init → first prototype + first validate), lightly annotated, lived at `QUICKSTART.md` at repo root, with one explicit "what can go wrong" sidebar.**

### 2a — Verbatim vs. curated

**Verbatim, lightly annotated.** Reasons:

- The whole *point* of the v0.10 dogfood is to produce honest external evidence (per §6 of the prior report). A curated QUICKSTART would re-introduce exactly the gap v0.10 closes ("kit pretends to be more polished than it is").
- Verbatim has a self-policing property: if a defect surfaces during the dogfood, the QUICKSTART can't ship until the defect is fixed (because the transcript would show the defect). This converts "QUICKSTART quality" into "kit quality" — they become the same artifact.
- "Lightly annotated" means: keep the actual transcript blocks verbatim, but add `> Note:` callouts where the user (you) had to make a judgment call that a first-time reader wouldn't naturally make. Don't rewrite the transcript; explain it.
- **Failure mode to avoid**: a transcript that shows the kit perfectly clean on the first try is more suspicious than one that shows a real recovery from a hiccup. If the dogfood truly produces zero defects, the QUICKSTART should explicitly note that the cycle ran clean — and that note is itself the headline evidence for v1.0.

### 2b — First session only or full first-week?

**First session only.** Specifically: `gmk-init` → `gmk-roadmap` (briefly) → `gmk-shape-advisor m1` → `gmk-prototype m1` → `gmk-validate m1` → stop after the first PASS verdict.

Reasons:

- The first-week workflow (`README.md:27-39`) is *7 skills deep* and the full chain ends at `/gmk-port`. A QUICKSTART that tries to cover all 7 is a tutorial, not a quickstart. The kit's onboarding cliff (per §3.2 of the prior report) is steepest at the *beginning*; that's where compression matters.
- The "first PASS verdict" is the moment a user has empirical evidence the kit works. Everything past that (self-test, merge-gate, port) is value-add but the user already believes by then.
- Cover the rest in a `WORKFLOW.md` or `FULL-WALKTHROUGH.md` *follow-up* doc — link to it from the end of QUICKSTART. Don't fold them together.

### 2c — Location

**`QUICKSTART.md` at repo root.** Reasons:

- `_workspace/quickstart.md` is wrong — `_workspace/` is the *user's project* output dir (`gmk-init:151`); the kit's own `_workspace/` is meta-artifact territory. A QUICKSTART in the kit's `_workspace/` would not survive a clean clone of the kit, and that's where new users would expect to find it. It also conflates two distinct meanings of `_workspace/`.
- `skills/_meta/QUICKSTART.md` is wrong — `skills/` is the plugin's skill directory; non-skill files there would either confuse the plugin loader or be ignored. Either way, undiscoverable.
- `QUICKSTART.md` at repo root is the GitHub convention; it surfaces in the repo file listing right next to `README.md`. The README's "First-week workflow" section (`README.md:27-39`) should add a one-line pointer: *"New here? See `QUICKSTART.md` for a real worked example."*

### 2d — Failure modes inclusion

**Yes, one explicit sidebar — but only the failure modes the dogfood actually hit. Not a synthetic list.**

The temptation is to write "here are the 5 things that can go wrong" — that's a troubleshooting guide, not a quickstart. The quickstart should be linear and short. But it should have one terminal section titled *"What can also happen"* listing only the real hiccups from the dogfood transcript (e.g., "if the prototype is non-deterministic, `gmk-validate` stops at the 2-pass seed check — here's what you'll see").

If the dogfood transcript is hiccup-free, this section reduces to: *"In this transcript, every command succeeded on first try. The kit's structural refusals (Rules 13-17, hook smoke fail, pillar shape mis-routing) didn't fire — see [link to RULES.md or prototype-rules SKILL] for what they look like when they do."* This is honest, short, and doesn't pretend to enumerate all possible failures.

**Reject** the "happy path only" version (omitting failure mode discussion entirely): the kit's whole identity (per `README.md:139-147`, `CONCEPT.md:343-348`) is structural refusals. A quickstart that pretends the kit never refuses misrepresents what the kit is.

## §3 — gmk-port 684-line resolution

**Recommendation: option (c) — declare SKILL.md files NOT subject to Rule 2 by design, with a one-paragraph clarification added to Rule 2 itself.** The split-decision artifact at `_workspace/v0.9-gmk-port-split-decision.md` already argues this; the v0.9 verdict's §3.3 hedged because option (c) wasn't on the table. With (c) explicitly on the table, it's the right answer.

### Why (c), not (a) split or (b) extend Rule 2

Re-reading `prototype-rules:58` as cited in the v0.9 verdict:

> *"300 is the median successful mechanic prototype across the kit's test corpus. 600 is the line where mental-model load exceeds what a single reader can hold while reasoning about state transitions. Beyond 600, prototypes consistently produce false PASS verdicts (the bot validates the wrong thing because the author lost track)."*

This rationale is mechanic-prototype-specific in three ways:
1. **"While reasoning about state transitions"** — SKILL.md files don't reason about state transitions; they document a procedure.
2. **"The bot validates the wrong thing"** — SKILL.md files aren't bot-validated. They have no falsification surface.
3. **"The author lost track"** — the failure mode is the *author writing code* losing track. A reader of SKILL.md doing a single-pass read or grep-jumping to a section header has a different cognitive profile.

The v0.9 split-decision document at `_workspace/v0.9-gmk-port-split-decision.md:46` already makes this argument: *"Rule 2 (300/600 line caps) targets `templates/prototype-*.html` mechanic prototypes, not SKILL.md reference docs."* The verdict's §3.3 hedged on this with *"the cap's own rationale applies to SKILL.md prose too"* — that was wrong on my part. The rationale is about *runnable* mental-model load, which SKILL.md doesn't carry the same way. The split-decision artifact's reasoning is correct.

**The credibility tension §3.3 identified is real but its resolution is the *opposite* of what I implied**: don't extend Rule 2 to SKILLs, don't split gmk-port. Instead, add ~3 lines to Rule 2 making the carve-out explicit so a future reader doesn't notice the same tension I did.

### Why not (a) split

Per the split-decision artifact at `_workspace/v0.9-gmk-port-split-decision.md:48-52`, the 6 stages of gmk-port are *operationally one flow* dispatched as a unit by `/gmk-loop`. Splitting would force users to remember which sub-skill to call when ("did I finish stage 5? do I run /gmk-port-rerun?"). This is UX cost for no benefit — the section headers already make the file navigable (`bash grep` on the file confirms 14 `^## ` headers and 5 `^### Stage ` headers — well-structured).

The closest natural split boundary is *not* Stage 5/6 (Stage 6 is only 17 lines, too small to extract). The split-decision artifact notes the only sizeable extraction candidate is `## What the bot validated` (159 lines at L443-601) — a per-mechanic reference catalog. Extracting it duplicates the Rule-14-style cross-reference burden and hides the catalog from the user actively reading the port flow.

### Why not (b) extend Rule 2 with allowlist

This is the worst of both worlds:
1. **It imports the prototype-cap mental model into a context where it doesn't fit.** A reader seeing "SKILL doc-cap: 500 soft / 1000 hard" will reasonably ask "why 500? where's the evidence the median successful SKILL is 500 lines?" There is no such evidence and producing it requires the kind of meta-corpus work the v0.5-v0.9 cycles already over-produced.
2. **The allowlist precedent (`marketplace.json:8` style)** is for catching *stale* allowlist entries, per `CHANGELOG.md:128-130`. An allowlist for a doc-cap would *grow* (every long SKILL gets an exemption), the opposite of the staleness-pattern the existing allowlist machinery is built to detect. It's an allowlist-shaped misuse.
3. **It re-opens the Rule-2-numbers debate** every time a SKILL grows. The v0.9 split-decision artifact's "re-open triggers" at L60-70 already gives the right policy: *re-evaluate on specific user/operational signals*, not on a number crossing.

### What to actually do

Add ~5 lines to `prototype-rules` Rule 2 (likely right after `prototype-rules:58`) saying explicitly:

> *Rule 2 governs `templates/prototype-*.html` and the prototypes generated under `prototypes/<name>.html`. It does not apply to SKILL.md reference documents, which are read non-linearly via section headers. See `_workspace/v0.9-gmk-port-split-decision.md` for the precedent and re-open triggers if a SKILL.md grows past 800 lines or develops structural smell.*

That is the entirety of the v0.10 gmk-port action. No split, no allowlist, no new rule. Just remove the tension by stating the carve-out the artifact already argued for.

### Magic-number questions (3a, 3b)

Don't ship answers to these. The premise that SKILL.md needs a cap is what's wrong. If you reject (c) and ship (b) anyway, then the magic numbers should be 500/1000 with `gmk-port` explicitly allowlisted up to 800 — but you'd be paying option-(b) cost for a problem that doesn't exist.

## §4 — Sequencing inside v0.10

**Recommendation: Option C-modified — gmk-port carve-out FIRST (5 lines, 10 minutes), then dogfood + QUICKSTART together, then v1.0.**

Concretely, an ordered timeline:

| Step | What | Duration | Why this order |
|---|---|---|---|
| 1 | Add the Rule 2 carve-out paragraph (per §3 above). Commit. | 30 min | This is 5-10 lines of doc + a CHANGELOG entry. It resolves a credibility tension that *currently exists*, before the dogfood transcript shows the kit operating with that tension unresolved. Doing it first means the dogfood runs against the v0.10 state, not v0.9 + a known-unresolved cap question. |
| 2 | Run `/gmk-init` on the dogfood project in a fresh non-kit directory. Capture full transcript. | 1 session | This is the "Critical blocker" closure. Don't shortcut. |
| 3 | Continue through `/gmk-roadmap`, `/gmk-shape-advisor m1`, `/gmk-prototype m1`, `/gmk-validate m1` until first PASS verdict — capturing transcript continuously. | 1-2 sessions | This is the QUICKSTART transcript material. Stop at first PASS for QUICKSTART scope. |
| 4 | Continue through `/gmk-self-test m1`, `/gmk-merge-gate`, `/gmk-port m1` to RE_PASS. Capture in a separate `WORKFLOW.md` or extended transcript. | 1-2 sessions | This is the "full chain proven" evidence (Critical blocker closure). |
| 5 | Add m2 + run inter-milestone path (`/gmk-regression`, `/gmk-merge-gate` against m1, optionally `/gmk-mechanic-merge` for m3). | 1-2 sessions | This is the multi-milestone evidence. |
| 6 | Collect defects observed during steps 2-5. Triage: real bugs vs. UX papercuts vs. doc gaps. | 30-60 min | This is the actual v0.10 backlog. |
| 7 | Fix the real bugs. UX papercuts and doc gaps go to v1.0.1 unless cheap. | varies (zero if dogfood is clean; 2-5 × 30 min per §6 of prior report) | Per the prior verdict's prediction. |
| 8 | Write QUICKSTART.md from step 3's transcript, lightly annotated, fix-mentions inline if any from step 7. | 1-2 hours | Now (and only now) the transcript reflects the *fixed* state. |
| 9 | Release v0.10 with: dogfood evidence (transcripts), QUICKSTART, Rule 2 carve-out, v0.10 defect fixes. | 1 session | Mid-step v1.0 candidate. |
| 10 | Wait one quiet release cycle. If no follow-up defects surface in real use, bump to v1.0. | days-to-week | The "external evidence" gate of the prior report. v0.10 itself is the evidence; v1.0 is the SemVer commitment. |

### Why not Option A (dogfood → fix → QUICKSTART → gmk-port → v1.0)

Option A is fine but puts gmk-port last, which means the dogfood transcript captures the kit *with the unresolved cap tension visible*. The Rule-2 carve-out is 30 minutes of work; doing it first is essentially free and means the dogfood runs against the v0.10 state.

### Why not Option B (dogfood + QUICKSTART simultaneously, verbatim including defects)

The "QUICKSTART includes defects + fixes inline" version is dishonest in the *other* direction — it ships a quickstart that reads like a debugging session, which is bad onboarding. The split-the-difference version (dogfood verbatim, QUICKSTART written from the *fixed* transcript with annotations) is what step 8 captures.

### Why not Option C (gmk-port first, then everything else)

Option C is what I'm recommending — but the original Option C reads like "resolve gmk-port via split". Resolving it via *carve-out* (§3 above) is 30 minutes, not the multi-hour split work Option C implied. With that correction, C is right.

### One sequencing risk to flag

The plural sessions in steps 2-5 mean the dogfood can take a calendar week even if the kit is bug-free. **Don't compress this**. The v0.5-v0.9 cycles' core failure mode (per §4 of prior report) was the meta-process running ahead of user evidence; compressing the dogfood to "do it all in one session" risks reproducing the same failure mode in v0.10 itself.

## §5 — Honest counter-questions

### 5a — "Process discipline tipping into perfectionism" framing

**I softened it. The harder version: the v0.5-v0.9 evaluator cycle is now a self-sustaining loop.** Evidence I had but understated:

- **The protocol corrects the protocol.** Per `CHANGELOG.md:11` (cited in §4 of prior report): *"Protocol 1 itself caught that 3 of 4 [M-2 dead branches] were live"* — i.e., the v0.9 cycle's first act was correcting its own protocol's framing of v0.8's output. That's *not* a healthy protocol — that's a protocol whose primary detection target is itself.
- **The closure criterion is plausibly unreachable.** Per §4 again: F21's "correction ratio < 1.0 for 3 consecutive releases" criterion is rising (1.75 → 2.80 → 3.00) *because the protocol template tightens*. A criterion that auto-recedes as you approach it is structurally a moving goalpost, not a falsifiable gate.
- **The meta-corpus is outgrowing the kit.** 778-line HANDOFF + 604-line CHANGELOG + 5 new v0.9-*.md files for one release. The v0.9 cycle alone shipped ~14 lines of behavioral change (Rule 16 annotation; `_save_breaking` removal) on ~2,000 lines of evaluator prose. The §3.5 framing of "the ratio is tilting" was accurate but I should have said "tilted, already past the point where additional cycle-work produces user-visible benefit."

The user's intuition (the framing they hinted at) is correct. **I hedged it because hedging is the safer rhetorical move with an author who has visibly invested in the meta-process** — not because the evidence was ambiguous. The evidence isn't ambiguous. The right verdict on v0.5-v0.9 is: v0.5-v0.6 were net-positive, v0.7 was marginal, **v0.8 and v0.9 should not have happened as evaluator cycles** — they should have been a dogfood and a v1.0 release respectively.

### 5b — Confidence in 40/35/25

**Medium confidence on the partition existing; lower confidence on the exact ratio.** If I re-grade more aggressively, the process-internal slice grows.

The hardening: several items I classified as "real" in the 40% are real-but-defensive (v0.7 `kit_version`, v0.8 `pillars.kind` — both annotated as "real but defensive" in the table). If "real" means *would have caused user-visible defects given a real user*, and no real user existed, then "defensive" items belong in the 35% bucket, not 40%. That moves the partition closer to:

| | Conservative read (what I shipped) | Aggressive read (more honest) |
|---|---|---|
| Real shipped-blocking | 40% | 20-25% |
| Defensive closures | 35% | 50-55% |
| Process-internal | 25% | 25-30% |

The "real shipped-blocking" floor is the v0.5 deprecation sweep (genuinely had stale-write defects users would have hit) and v0.8 Check B promotion (real bug in the guard itself). Those are unambiguous. Everything else is on a defensive ↔ real continuum, and my 40% rounded toward "real" because (a) I didn't want to be uncharitable, and (b) the items are *defensible*, just not *load-bearing*.

The aggressive read is more honest. I should have shipped it.

### 5c — Confidence in "2-5 real defects, 30 min each, v1.0 in 2 weeks"

**Medium confidence on the *shape* of the prediction; low confidence on the specific numbers.**

What I'm confident about:
- **At least one defect surfaces.** A kit this complex, never run end-to-end on a non-author project, is too good to be true if zero defects surface. If zero surface, my prior is that the dogfood wasn't thorough enough (e.g., a user reading transcripts in a hurry rather than actually running commands and checking outputs).
- **The defects are small.** The kit's internal consistency is genuinely strong (§2.4 of prior report); inconsistencies have been actively hunted. So defects are most likely in the *handoff between skills* — exactly where the bot smoke and 5-stage gates are designed to catch them.

What could surprise me:
- **A defect in the bot hook library itself.** `_bot_hook_lib.js` was reviewed but only against the prototype templates that ship with the kit. A genuine user-authored prototype using the hook in a slightly-off way could surface a hook library defect (e.g., an unhandled crash path in `makeHook`'s persona-callback degradation at L197-229). This would be more than 30 min to fix — it would be a hook API revision.
- **The 5-stage `gmk-port` flow on a non-trivial Godot port.** Stages 2-3 (engine compile, engine smoke) have never been exercised against a real Godot project in the repo's git history. Surprises here (e.g., Godot 4 CLI version differences, scene-vs-script convention mismatches that the conventions-read at `gmk-port:74-77` doesn't catch) could be multi-hour, not 30-min.
- **Cumulative onboarding friction.** Not a defect per se, but: the kit demands a lot of context (§3.2 of prior report). Even if every skill works as specified, the *integration cost in the user's head* could be the actual blocker. This is unfalsifiable in solo dogfood (the author already knows the context); it only surfaces if a second person runs the dogfood. That's a v1.0.1 or v1.1 risk, not v0.10.

If I had to ship a single most-honest prediction: **"3 real defects (1 in inter-skill handoff, 1 in gmk-port Stage 2-3, 1 doc-gap), with 70% confidence the inter-skill one is <30 min, 50% confidence the gmk-port one is <2 hours, and ~10% chance of a hook-library surprise that takes the whole v0.10 cycle 3-4 weeks instead of 2."**

The 2-week estimate in §6 of the prior report was the median; the right *expected* timeline including the hook-library tail risk is 2-3 weeks. Still v1.0-shippable within the month.

The single biggest correction to my own report is §5a: the meta-process loop is more self-sustaining than I framed, and the user's intuition on that was correct.

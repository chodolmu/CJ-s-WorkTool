## Two paths considered

### Path (a) — Make it read

Add a precondition in `gmk-save-migrate`: if the milestone has `_save_breaking: false`, write a noop migration record and skip plan generation. Introduce as Rule 18 (mirroring Rule 16 / Rule 17 read-contract pattern), add a 4-row table, amend SKILL footers, add Check H to `check-plugin-meta.sh`.

**Cost**: high. New rule, new footer amendments, new structural check, new SKILL behavior. Adds a *declared convention* that needs ongoing maintenance.

**Value**: enables users to acknowledge a non-breaking persistence change without running the full `/gmk-save-migrate` flow.

### Path (b) — Drop the suggestion

Edit `gmk-merge-gate:156` to remove the `_save_breaking: false` mention. Warning text becomes: *"Either run `/gmk-save-migrate <id>` or confirm the change is non-breaking before merge."* The field disappears from the kit entirely.

**Cost**: 1-line edit.

**Value**: eliminates the half-applied class. 0 readers + 0 writers + 0 mentions = nothing to maintain.

---

## Decision: Path (b)

**Reasons**:

1. **Single mention, no users**. The field is mentioned in exactly one warning string. No milestone in any in-repo fixture uses it; no user has been observed adopting it (the kit's been live for v0.4 through v0.8 with the warning text unchanged). Adding a reader for a feature 0 users use is over-engineering.

2. **The user-acknowledgment path already exists without the field**. `gmk-save-migrate` Step 5.5 (`gmk-merge-gate:159`) already documents that the warning is *"a doc the user can write next"* — i.e., the user responds to the warning by running `/gmk-save-migrate`, or by deciding the change is non-breaking and proceeding to merge anyway. The field added nothing the user couldn't already do; it just gave the absence of a save-migration file a structured shape that no SKILL ever consumed.

3. **Rule 18 would add a *declared convention* to maintain**. Each declared rule has ongoing maintenance cost: footer amendments, structural-guard updates, evaluator scope every release. Rule 18 for a 1-mention 0-reader field would be a net-negative for kit overhead. The kit's discipline is *closing* half-applied conventions, not adding more.

4. **Minimal-surface principle for v1.0**. v0.9 is the last v0.x. The v1.0 backward-compat inventory (T2-C, written in this same cycle) should have *zero* "declared-but-half-applied fields" entries. Path (a) would keep `_save_breaking` on the inventory ("now a stable read contract — must not break"). Path (b) removes it from the kit's API surface entirely — nothing to inventory, nothing to break.

5. **Symmetric to v0.7's Rule 14 CYCLE preservation reasoning**. v0.7 *kept* the Rule 14 CYCLE form as a safety valve because (a) the rule was actively cited elsewhere and (b) future scenarios might fire it. Neither applies here: `_save_breaking` is not cited as a fallback for anything else, and the future scenario it would fire on (user wants to acknowledge non-breaking without running save-migrate) is already served by the user just running merge-gate again after manual confirmation.

**공식 문서가 구분하는 4개 경로** ("Choose the right approach" 표):

| 기능 | 트리거 | Claude 실행 위치 | 셋업 | γ 모델 정합 |
|------|--------|------------------|------|-------------|
| **Dispatch** | 모바일 앱에서 task 메시지 | 사용자 PC (Desktop 앱) | 모바일↔Desktop 페어링 | ★ "away 위임 + 최소 셋업" — γ 모델("모바일 트리거→PC 실행")에 **가장 가까움** |
| **Remote Control** | 도는 세션을 claude.ai/code or 모바일 앱에서 조종 | 사용자 PC (CLI/VS Code) | `claude remote-control` 실행 | "in-progress 작업을 다른 기기에서 조종" — 트리거보다 *조종* |
| Channels | Telegram/Discord push 이벤트 | 사용자 PC (CLI) | 채널 플러그인 설치 | concept 원래 명세. 봇 셋업 필요 |
| Claude Code on web | claude.ai/code에서 시작 | **Anthropic 클라우드** | 없음 | ✗ 로컬 파일 접근 불가 |

**확정 사실 (공식 문서)**:
- `claude remote-control` server mode + `--name "..."` 옵션 실재. `--remote-control`(`--rc`) interactive, `/remote-control` 기존 세션 변환도 실재. **명령 이름은 web 주장이 아니라 문서 확정.**
- 푸시 알림: v2.1.110+ (`/config` → "Push when Claude decides"). Remote Control v2.1.51+.
- **핵심 제약**: *"The web and mobile interfaces are just a **window into that local session**."* → 모바일은 로컬 세션의 *창*. **모바일 브라우저가 PC의 `file://` 빌드를 직접 못 연다. 모든 상호작용은 채팅 세션 매개.** (Codex BLOCKER-1 맞음.)
- 세션 죽음: PC sleep는 자동 재연결 / **네트워크 10분+ 끊김은 timeout으로 process 종료** (재시작 필요). Ultraplan과 동시 사용 불가.

**그래서 정정 2가지**:
1. **메커니즘**: Telegram/Discord 봇(Channels) → **Dispatch 또는 Remote Control** (둘 다 봇 토큰 0, 공식). 어느 쪽인지는 §0a에서 결정.
2. **모바일 빌드 "재생" 가정 폐기**: 모바일이 file:// 빌드를 못 여니, 컨펌은 *채팅 매개*(S4 paste-to-chat 경로)로만. S4 설계가 정확히 이 제약에 맞음 — 빌드 파일을 모바일이 열 필요 없이 agent가 milestones.json 기록.

**P7 정합**: P7의 *원칙*("자체 runner 짓지 말고 Claude Code 네이티브 기능 위에 얹어라")은 **Dispatch/Remote Control 둘 다 봇보다 강하게 충족**. Telegram/Discord 봇(Channels)은 *채널 플러그인 설치*가 필요 = 작은 자체 인프라 — 함정 1의 약한 재현. Dispatch/Remote Control은 그 설치조차 0.

**→ concept §3/P7의 *명시된 메커니즘*(Telegram/Discord)은 이제 *열등한 경로*다. concept-level 명세 오류 = RE-OPEN 후보 (§8).** 이 detail은 올바른 경로로 쓰되, concept lock을 침묵으로 거스르지 않고 §8에 RE-OPEN 후보를 명시하여 사용자 비준에 넘긴다.

## §0a 메커니즘 선택 — Dispatch vs Remote Control (사용자 결정)

둘 다 γ 모델에 맞지만 성격이 다름:
- **Dispatch** = 모바일에서 *task를 던지면* Desktop이 세션을 spawn. "away 위임"에 최적 = 사용자 γ 모델("모바일 트리거→PC가 cycle 1회 진행")에 **개념적으로 가장 정확**. 단 Desktop 앱 페어링 필요.
- **Remote Control** = PC에서 세션을 *먼저 띄워두고* 모바일이 조종. 셋업 단순(`claude remote-control` 한 줄)하나 "트리거"보다 "조종" 모델.

**이 detail은 Remote Control을 primary로 가정** (셋업 가장 단순 + CLI만으로 가능, Desktop 앱 의존 없음). 단 §0의 표가 보여주듯 Dispatch가 γ 모델에 더 정확하므로, §2 실행 전 사용자에게 어느 경로인지 확인 (AskUserQuestion). Dispatch 선택 시 Step 1-2가 "Desktop 페어링"으로 바뀜 — 그 분기는 사용자 결정 후 detail patch.

## §3 Pass/Fail (artifact-level, P2)

- **PASS** = Step 3 gate(모바일 트리거 → PC 실행 → 모바일 결과 표시) 성공 + Step 4 컨펌 round-trip 성공(모바일 트리거→milestones.json 갱신 도달). = 모바일 1대로 PC 로컬 gmk 프로젝트를 *트리거하고 컨펌*할 수 있음. (빌드 *재생*은 PC 화면 — §0 한계.)
- **부분 PASS = 푸시 알림만 누락** (트리거+컨펌 round-trip은 OK). → S7 진입 가능. **단 푸시 누락은 *그냥 무시 아님*** (Codex HIGH 반영): 푸시 없이 *수동 폴링*에 의존하면 latency가 직접 작업보다 느려질 수 있고, 이는 **concept S7 quit signal(line 176 "dispatch latency가 직접 작업보다 느리면 STOP")의 직접 후보**다. → 부분 PASS 시 `s6-verdict.md`에 "푸시 누락 = S7 latency quit signal 후보"를 *명시적 학습*으로 기록하고, S7 detail이 이를 첫 risk로 받음. 푸시가 끝내 안 되면 concept Layer 3의 "알림" 요구가 미충족이므로 §8 RE-OPEN 시 사용자에게 "Channels(봇) 알림 보강 여부"도 함께 물음.
- **FAIL/STOP** = (a) Step 1 eligibility 실패(구버전/API key/admin off) → §4 fallback 분기 / (b) Step 3 모바일 트리거 안 잡힘 → concept S6 quit signal hit, STOP.
- **사용자 시간 cap**: S6은 *셋업*이라 사용자 손이 많이 감. 셋업이 30분 넘으면 STOP하고 부분 진행을 resume에 기록(P8) — "한 phase 더만" 금지(handoff 경고: 사용자 구독 해지 고민 중). Step 1-4 각각이 "auth/네트워크/모바일 재시도 한 번 더"를 부를 수 있음(Codex MEDIUM) — 각 Step fallback은 *1회 재시도*로 cap, 반복 실패 시 STOP.

## 1. Why (사용자 목표)

> *"별다른 지시 없이도, 리서치를 통해, 게임다운 게임을, 스스로 계속, 입력 없이도 만들 수 있어야 한다."*

γ 모델: **seed 1회 + 자율 진행 + 플레이 가능한 빌드마다 컨펌**.

**Taste 문제 해법**: kit이 "재미" 판정 안 함. **검증된 레퍼런스를 베끼는 것**으로 우회. 사용자가 플레이하고 *차별화 피드백* 줄 때까지 kit은 clone.

## 2. Scope

| 하는 것 | 안 하는 것 |
|---------|-----------|
| Reference-clone-first 자율 게임 빌드 | 출시 도구 (후속 단계) |
| 장르 컨벤션 자율 리서치 | IP boundary (사용자 책임) |
| Module 단위 milestone | "재미" judgment (사용자 피드백으로만) |
| Playable build마다 사용자 컨펌 | 차별화 디자인 결정 (사용자 피드백 기반) |
| 캐릭터/스토리 *제외* 모든 베끼기 OK | 캐릭터/스토리는 임의 채움 (사용자 출시 전 교체) |

**핵심**: kit은 **clone-to-validate 도구**. 출시 도구 아님 → IP 함정은 사용자 다운스트림.

## 3. Architecture (4-layer)

```
[사용자 seed] (예: "merge3 / cozy / PC Steam / Royal Match 비슷한")
        ↓
Layer 1   — Autonomous Reference Research
            (WebSearch+WebFetch로 레퍼런스 분해 + 컨벤션 추출 + anti-trope 추출)
        ↓
Layer 1.5 — Reference-to-Production Translation
            (research → 기계 검사 가능한 production contract 변환)
            ★ 사용자 컨펌 게이트 1
        ↓
Layer 2   — Module-Based Milestone Execution
            (module = 분리 가능한 playable 단위. 예: Royal Match면 M1=3매치 / M2=아웃게임 / M3=스킬+BM / M4=에디터)
            ★ Module마다 컨펌 게이트
        ↓
Layer 3   — Dispatch-based Mobile-Trigger Cycles
            PC 켜둠 + Claude Code 백그라운드 worker 활성화
            사용자가 모바일에서 "다음 module dispatch" 트리거
            PC가 cycle 1회 (module 1개 빌드) 진행
            결과 Channel(Telegram/Discord) 알림
            사용자 1분 컨펌 → 다음 module 모바일 트리거
            * 야간 무인 X (사용자 의도적 제외)
            * 5h 한도 = cycle 크기 cap (module 1개는 5h 내 끝남)
```

**Layer 분리 원칙**:
- Layer 1 = 연구 / Layer 1.5 = 번역 (연구→생산 계약) / Layer 2 = 생산 / Layer 3 = 자동화
- Layer 1.5가 빠지면 Layer 1 결과가 prose로 끝나서 Layer 2가 못 씀

## 4. Core Principles (검증 통과 항목 — 절대 양보 안 함)

### P1 — Machine-parseable contract
genre-decisions는 prose 금지. **기계가 검사할 수 있는 형식** (JSON 또는 strict markdown sub-schema). Layer 2/3 모든 호출이 fresh read 함.

→ *구체 schema는 detail plan에서 결정*

### P2 — Artifact-level quit gates
모든 quit gate는 **observable artifact 신호** (git log / file check / count). feeling-based gate 금지 ("사용자가 만족 안 함" 같은 표현 사용 금지).

→ *구체 gate 문구는 각 S detail plan에서 결정*

### P3 — Dogfood validity defense
사용자가 *이미 잘 아는 장르*로 dogfood 돌리면 Layer 1이 나빠도 사용자 머릿속이 채움 = false PASS. 그래서 **dogfood 2개**:
- (A) 사용자가 모르는 장르, Layer 1+1.5만 (research가 사용자가 모르던 mandatory convention ≥1개 surface)
- (B) merge3 M1 full build (워크플로 검증)

→ *모르는 장르 선정은 detail plan에서 사용자와 결정*

### P4 — Module-axis milestone
milestone = **분리 가능한 playable module 1개**. 시간 축 아님 (5분/10분 X). 더 작아도 됨.

### P5 — Check-in per playable build
모든 playable build마다 사용자 컨펌. exe 아니어도 됨. .html 시각 컨펌 (핵심 + 시각 자료).

### P6 — JIT detail planning
이 concept plan은 *방향만*. **각 S의 detail plan은 그 step 진입 직전에 작성**. 이전 step의 학습이 다음 step detail에 반영.

→ TaskForge Pro의 검증된 패턴 차용

**Enforcement**: 각 S detail plan은 `v1.0-detail-backlog.md`의 *체크리스트 통과 후*에만 실행 가능. 체크리스트 미통과 detail은 reject.

### P7 — Use Claude Code Dispatch, don't build runner
v0.10 자산 (auto-runner, runner/*) 직접 재사용 X. **Layer 3은 Claude Code의 Dispatch 기능 위에 얹음** — OS-level Node runner / Windows Task Scheduler 같은 *자체 인프라 짓지 않음*.

Dispatch 작동 방식:
- PC에 Claude Code 백그라운드 worker 활성화 (sleep 막아둠)
- 사용자가 모바일 (claude.ai 웹/앱)에서 *같은 계정 로그인* → 명령 트리거
- PC가 dispatch 받아서 *별도 background process*로 cycle 1회 진행
- 결과를 Channel (Telegram/Discord)로 *모바일에 알림*

→ 사용자가 *PC 앞에 안 앉아도* 게임 개발 진행 가능. 출근 길/침대에서 1분 단위 인풋.

5중 patch gate / baseline-lock / D-013 방어 같은 *v0.10 logic*은 *Dispatch worker의 prompt에 박힘* (코드 형태가 아니라 SKILL 단계로). 코드 폐기, 아이디어는 SKILL로 재구현.

### P8 — Session Continuity Required
사용자 제약: 1-2h/day + Claude Code 5h 세션 한도 + 컨텍스트 가득 차면 handoff + clear. 모든 작업은 **언제든 끊겨도 다음 세션이 이어받음**을 가정해야 함.

**원칙**:
- 모든 산출물은 **atomic write** (중간 상태 파일 시스템에 안 남김 — write-temp-then-rename)
- 각 step (S0/S1/S1.5/...) 끝마다 **resume point 파일** 갱신 (`_workspace/v1.0-resume.md`)
- HANDOFF.md 갱신이 step 완료의 *일부* (별도 작업 아님, 빼먹으면 step 미완료)
- 새 세션이 다음 3개 파일만 읽으면 *완전히 이어받음*:
  1. `v1.0-concept.md` (LOCKED, 매 세션 시작 시 읽음)
  2. `v1.0-resume.md` (가장 최근 step 상태 + 다음 액션)
  3. 진행 중인 step의 `v1.0-detail-S{N}.md`

**Anti-pattern**:
- "이 step은 한 세션에 끝남"이라고 가정 → 새 세션이 *처음부터 재시작*
- 산출물이 *partially written* → 새 세션이 *현재 상태 못 알아봄*
- HANDOFF 갱신을 *나중에* → 끊김 발생 시 *지난 일 잊어버림*

**Enforcement**: 각 detail plan은 *resume point 파일에 박힌 내용 + 그 시점 wall time*을 step 끝 산출물로 명시. 빠지면 detail reject.

**Critical — Resume Verification Rule**: `v1.0-resume.md`는 *paranoid new session에 대한 힌트지 계약 아님*. 각 detail의 모든 Step N은 *첫 sub-step으로* 이전 step의 claimed artifacts를 *disk/git 실제 상태에서* 검증해야 함 (파일 존재 / git ref 존재 / 내용 sanity check). resume.md만 믿으면 partial-write 케이스에서 D8 drift back-door로 재현됨.

→ 이게 **γ 자율의 실현 메커니즘**. *사용자 attention*은 1-2h/day이지만 *작업 진행*은 multi-session continuous로 보임.

## 5. Sequencing (골격만 — detail은 각 S 직전 JIT)

| Step | 무엇 | Concept-level quit signal |
|------|------|---------------------------|
| S0 | v0.10 freeze | (cleanup, gate 없음) |
| S1 | Layer 1 (gmk-init 재설계) | Layer 1이 사용자 외부 리서치 없이 작동? |
| S1.5 | Layer 1.5 schema 정의 + gmk-genre-decide SKILL | P1 위반 시 STOP |
| S2 | unfamiliar genre mini-dogfood (Layer 1+1.5만) | research가 사용자가 모르던 convention 못 surface하면 STOP |
| S3 | Layer 2 (gmk-module-build) | module이 playable 아니면 STOP |
| S4 | gmk-confirm SKILL (.html 시각 컨펌) | 사용자가 .html 무시하고 코드 들여다보면 STOP |
| S5 | merge3 M1 full dogfood (local) | 1-2h 이상 사용자 시간 들어가면 STOP |
| S6 | Dispatch 통합 — PC background worker + Channel 알림 설정 | Dispatch trigger가 모바일에서 안 잡히면 STOP |
| S7 | M2 dispatch dogfood (Dispatch로 module 1개 끝까지) | dispatch quota/latency가 직접 작업보다 느리면 STOP |

**Stop 의도**:
- S5까지: M1 dogfood로 *워크플로* 검증 (Dispatch 없이도 됨)
- S6-S7: Dispatch 통합 검증 (모바일 트리거 + Channel 알림 작동하나)
- 전체 게임 빌드 아님 — 패턴 반복은 M3 이후 자율

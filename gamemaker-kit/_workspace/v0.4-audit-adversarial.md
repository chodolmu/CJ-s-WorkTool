## AD-1 — orphan flag 추가 발견: `--accept-regression`

**위치**: `skills/gmk-regression/SKILL.md:157, 179, 238`

```
/gmk-validate m2-dragon-evo --accept-regression — only if the regression is acceptable
Captures regression-trial data; user explicitly accepts via /gmk-validate <m> --accept-regression
```

- `--rebaseline` — 기존 baseline 덮어쓰기

- (`--skip --reason "..."` v0.4 W1에서 추가 검토)

## AD-2 — `gmk-port --force-rebuild` 부분 orphan

**위치**: `skills/gmk-port/SKILL.md:490, 516` (사용), `:638-648` (`--stage N` 섹션, force-rebuild는 *언급 없음*)

**증거**: SKILL 본문에서 추천하지만 정식 정의 섹션 부재. `--stage 1` 재실행과의 차이가 모호.

**영향**: RE_FAIL 후 사용자가 `--force-rebuild` 호출 → SKILL이 `--stage 1`로 해석할지, 다른 이론 동작인지 불명. 코드 변경 위험 (Stage 1이 *spec*만 다시 만들지 *기존 코드 덮어쓰기*하는지).

**심각도**: ★★ — 데이터 손실 가능 (사용자의 hand-tuning이 덮어써짐).

**제안**: `--force-rebuild` 정식 정의 또는 본문에서 `--stage 1` 표현으로 통일.

## AD-3 — Milestone-id mis-typing 처리 일관성 부족

**위치**: 27/29 SKILL이 `<milestone-id>` 인자를 받음. *graceful list-and-stop* 명시는 `gmk-validate` 한 곳 (`SKILL.md:30`).

**증거**: grep `id === <name>` / `find an entry` → 2 file hit. 나머지 25 SKILL은 사용자가 typo 입력 시 *행동 명시 없음*.

**영향**: 사용자가 `gmk-design-system m2-tipo`(오타) 호출 → SKILL이 (a) 모든 milestones 나열, (b) 첫 entry로 진행, (c) 실행 자체 거절 — 셋 다 가능. 일관성 부재.

**심각도**: ★★ — 빈번한 사용자 실수 (id 복사붙여넣기, 자동완성 미사용). 27 SKILL 일괄 fix 비용 큼.

**제안**: 공통 helper 패턴 명문화:
- "Notes for model" 섹션에 1줄 추가: *"If `<milestone-id>` not found in `milestones.json`, print available IDs and stop. Do not auto-select."*
- 또는 `gmk-prototype-rules`에 *milestone-id resolution* 공통 규약 추가, 다른 SKILL이 citation.

## AD-4 — `--force` 의미가 SKILL마다 다름

**위치**: `--force`는 7 SKILL에서 사용 (`gmk-self-test`, `gmk-narrative`, `gmk-ux-flow`, `gmk-port`, etc.).

**일관성 점검**:
- `gmk-port`: `--force` → `forced: true` 영구 stamp + 3-line warning
- `gmk-self-test`: `--force` → 일회성 override, milestone에 기록 안 됨
- `gmk-narrative`: `--force` → 일회성 override, shape 무관하게 실행
- `gmk-ux-flow`: `--force` → validation 미통과 milestone에서 실행 허용

**영향**: 같은 플래그 이름이 SKILL별로 *영구* vs *일회성* 다르게 작동. 사용자가 `--force` 의미를 일반화 못 함.

**심각도**: ★ — UX 결함이지만 단일 결함 아님.

**제안**: 명명 분리
- 영구 stamp가 남는 경우 → `--force` 유지
- 일회성 override → `--override` 또는 `--bypass`
- 또는 본문에 각 SKILL의 `--force` semantics 명시 라인 추가

## AD-5 — refuse 메시지의 "다음 step" 추천이 dead-end로 가는 경우

**Trace 사례**:
1. 사용자가 `gmk-self-test m1` 호출
2. Precondition `validation` missing → refuse: *"Run /gmk-validate first."* (SKILL.md:32)
3. 사용자가 `gmk-validate m1` 호출
4. 만약 m1이 `shape: 'shader'` 이거나 hypothesis가 bot-only 아니면 → INCONCLUSIVE 가능
5. INCONCLUSIVE 후 self-test 권유 (`gmk-validate` Step 4 verdict block)
6. 사용자가 `gmk-self-test m1` 다시 호출 → 이번엔 통과? 일부 시나리오에서 *precondition 만족하지만 self-test row가 placeholder PASS* (CR-6) → 행동 모호

**일반 패턴**: 한 SKILL의 refuse가 다른 SKILL로 보내는데, 그 SKILL도 비슷한 조건으로 refuse하는 *순환 가능성*. v0.3가 cycle 검증을 명시적으로 안 함.

**심각도**: ★★ — flow chain의 일부 시나리오에서 사용자 막힘.

**제안**: 
- (a) v0.3 Wave D의 "호출 그래프 보강"을 cycle detection도 포함하도록 확장
- (b) 각 SKILL의 refuse 메시지가 *다음 SKILL을 추천*할 때, 그 SKILL의 precondition도 함께 확인하는 cross-link

## AD-6 — `gmk-loop` lock 우회 시 데이터 일관성 보호 안 됨

**위치**: `skills/gmk-loop/SKILL.md:59, 217`

```
.gamemaker-kit/.loop.lock 이 있으면 refuse. 사용자가 sure하면 manually delete.
```

**시나리오**: 두 세션이 동시에 같은 milestone을 만짐 → 한 세션이 lock 만들고 작업 중인데 다른 세션 사용자가 *manually delete* → 두 세션이 동시에 milestones.json 쓰기 → race condition / 데이터 손상.

**영향**: lock manual-delete escape hatch가 *진짜로 stuck인 경우*와 *현재 작동 중인 다른 세션*을 구분 못 함.

**심각도**: ★ — 실제 발생 빈도 낮음 (다중 세션 + 같은 milestone), 단 발생 시 데이터 손상.

**제안**: lock 파일에 PID + hostname 같이 적기 → manual delete 시 *그 PID가 살아있는지* 검사 후 delete. 또는 60min 자동 expire 정책 (CR-8과 묶음).

## AD-7 — Precondition refuse 메시지의 다국어 일관성

**위치**: SKILL.md 본문이 한국어와 영어 혼재. refuse 메시지도 대부분 영어, 일부 한국어 자연어.

**영향**: 사용자(한국어 사용자)가 한국어 명령 ("막힌 마일스톤") 후 refuse는 영어로 받는 경우. CLAUDE.md "비개발자도 쉽게 사용" 정책과 약한 충돌.

**심각도**: ★ — 비핵심.

**제안**: 정책 결정 — refuse 메시지를 영어로 통일 vs 사용자 언어에 맞춤. 현재는 *영어로 통일*인 것 같으나 명시 안 됨.

## AD-9 — Empty / partial state 처리 미명시

**시나리오들**:
- `milestones.json`이 있지만 `milestones: []` 빈 배열일 때 SKILL 행동? 일부는 명시 (gmk-roadmap, gmk-dev-complete), 다수는 미명시.
- `pillars.json`이 `pillars: [], skipped: true` 일 때 SKILL 행동? `gmk-prototype`만 명시 (warn + 사용자 확인 후 진행).
- `.gamemaker-kit/` 폴더가 있지만 내부 비어 있을 때?

**영향**: 신규 사용자가 `gmk-init` 미실행 + 다른 SKILL 호출 → 일부는 친절히 안내, 다수는 throw / 모호.

**심각도**: ★★ — 보일러플레이트지만 27 SKILL 일괄 영향.

**제안**: 공통 precondition pattern 명문화 (AD-3과 같이 묶음). `gmk-prototype-rules`에 추가하거나 별도 referenced file.

## AD-10 — Agent의 SKILL refuse 메시지가 SKILL과 동기화 안 됨

**위치**: 4 agents — `systems-designer`, `feel-engineer`, `economy-balancer`, `playtest-analyst`.

**점검**: agent description은 "X가 없으면 refuse"라고 함. 예: `systems-designer` agent는 *"Refuses to work without pillars.json and at least one target milestone in milestones.json."*

**영향**: SKILL이 agent를 추천하면서 정확한 precondition을 노출 안 함. 사용자가 `@systems-designer` 호출 → agent가 거절 → 사용자가 SKILL 다시 호출 → 같은 정보를 다시 묻는 *bounce* 가능.

**심각도**: ★ — frequency 낮음.

**제안**: 4 agent 각각의 precondition을 SKILL에 인용. v0.3 Wave A의 wiring이 *조건*도 함께 명시하도록 보강.

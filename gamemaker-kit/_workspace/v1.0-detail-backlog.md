# v1.0 Detail Plans — Backlog

**Purpose**: Concept plan (`v1.0-concept.md`)이 lock된 후, 각 S 진입 직전에 작성될 detail plan들의 *목록과 작성 시점*.

**원칙**: JIT (Just-In-Time) planning. Detail은 *해당 step 직전*에 작성. 이전 step의 학습이 다음 detail에 반영.

---

## Resume Point 파일 (`_workspace/v1.0-resume.md`)

P8 enforcement용. **모든 step 끝마다 *자동 갱신*. 새 세션 진입 시 *처음 읽는 파일***.

### 형식 (machine-parseable, 한 페이지 이내)

```markdown
---
status: in_progress | step_done | blocked | dogfood_pass
current_step: S0 | S1 | S1.5 | S2 | S3 | S4 | S5 | S6
last_updated: 2026-MM-DD HH:MM TZ
wall_time_total_min: <누적>
session_count: <세션 갯수>
---

# v1.0 Resume Point

## 지금 위치
- Step: {current_step}
- Status: {status}
- 마지막 산출물: {file path + line, 또는 commit SHA}

## 새 세션에서 *바로* 다음에 할 것 (1줄)
{명령형 한 줄, 예: "v1.0-detail-S1.md 작성, S0 학습 기록 §S0 학습 섹션에서 읽음"}

## Blocked 상태인 경우 — 사용자 결정 대기 항목
{있으면 명시, 없으면 비움}

## 이번 step의 학습 (다음 detail 작성에 반영)
{step 끝나기 전 마지막 갱신 — 한 줄짜리 bullet 3-5개}

## 의존성 (다음 step이 가정하는 것)
- {파일 path}: 존재해야 함, 내용은 {요약}
- {SKILL name}: 동작해야 함, 변경 없음

## 위험 신호 (있으면 다음 세션이 *멈추고 확인*)
- {예: "S0 Step 3에서 archive 브랜치 remote push 실패. 로컬만 있음. 새 세션은 push 재시도부터."}
```

### Atomic write 규약
- `v1.0-resume.md`는 *write-temp-then-rename* 으로만 갱신. 절대 in-place 편집 안 함.
- 새 세션이 *읽다가 partial state를 만나는 것* 방지.

### 새 세션 진입 시 표준 절차 (3 파일 read)
1. `v1.0-concept.md` 정독 (방향 + P1-P8 원칙)
2. `v1.0-resume.md` 정독 (현재 위치 + 바로 다음 액션)
3. resume이 가리키는 `v1.0-detail-S{N}.md` 정독 (구체 step)

→ 위 3개만 읽으면 *완전히 이어받음*. 다른 conversation history / handoff prose / chat log 불필요.

## 각 Detail Plan에 *반드시* 들어가야 할 것 (체크리스트)

각 detail plan 작성 시 아래가 빠지면 evaluator/Codex의 D1 (executable?) WEAK 재현:

### 모든 detail plan 공통
- [ ] 5-10 단계의 numbered procedure (concept의 한 문장을 풀어내기)
- [ ] 입력 (어떤 파일/state 읽음) / 출력 (어떤 파일 생성/수정) 명시
- [ ] **Artifact-level quit signal** (P2 위반 시 detail 재작성)
- [ ] 의존 검사 (직전 step 산출물이 무엇이 있어야 진행 가능)
- [ ] 실패 시 fallback (정의 안 하면 진행 중 즉흥 결정 = drift)
- [ ] **Session continuity (P8)**:
  - [ ] 각 numbered step 끝마다 *resume point 갱신 명령* 박힘 (어느 시점에 끊겨도 다음 세션이 그 다음 step부터 이어받음)
  - [ ] 모든 산출물 *atomic write* 명시 (write-temp-then-rename, partial state 금지)
  - [ ] HANDOFF.md 갱신이 detail의 *마지막 step* (별도 작업 아님)
  - [ ] *세션 끊김 발생 시 새 세션이 무엇을 읽어야 하나* 명시
  - [ ] 각 step 끝나면 *현재 step 번호 + wall time + 다음 액션*이 resume point에 1줄로 박힘
  - [ ] **Resume verification first sub-step**: 각 Step N의 *맨 처음 sub-step*은 이전 step claimed artifacts를 *disk/git 실제 상태에서* 검증 (파일 존재? git ref 존재? 내용 sanity?). resume.md만 믿으면 reject.

### Schema 관련 detail plan (S1.5)
- [ ] **JSON vs strict markdown 선택 + 이유**
- [ ] 모든 필드 type + required/optional
- [ ] ID format 정의 (예: `C\d+` / `A\d+` / `M\d+`)
- [ ] Layer 2가 *기계적으로 어떻게 파싱*하나 (정규식? JSON.parse? markdown AST?)
- [ ] schema 위반 시 어떻게 reject

### SKILL 재설계 detail plan (S1, S3, S4)
- [ ] 기존 SKILL.md 정독 + 어떤 줄이 살고 어떤 줄이 갈지 명시
- [ ] 새 Step procedure (기존 gmk-* SKILL 형식 따름)
- [ ] 다른 SKILL과의 contract 변경 (어떤 SKILL이 영향받나)
- [ ] Frontmatter (description, trigger keywords)

### Dogfood detail plan (S2, S5)
- [ ] Pass/Fail 정의 (artifact-level, P2 따름)
- [ ] 사용자 시간 cap (concept S5 quit signal 따라)
- [ ] 실패 시 무엇을 학습으로 기록

## Deferred Items 추적 (concept §8에서 가져옴)

이 항목들은 concept에 박혀있지 않지만 *어떤 detail plan에서 풀릴지* 예상:

| Deferred Item | 풀릴 곳 |
|---------------|---------|
| Confirmation latency 디자인 | S4 detail (또는 첫 컨펌 wait 발생 시) |
| Module decomposition 출처 | S1.5 detail (schema 짤 때 자동 결정) |
| "Playable" 정의 (HTML vs Godot) | S1.5 detail (acceptance 필드에 흡수) |
| SKILL 매트릭스 전수 분류 | 매 SKILL touch detail에서 그 SKILL만 분류 |
| `ddbfb9b` 처리 | **S0 detail** |
| Layer 1 비용 cap | **S1 detail** (WebSearch 패턴 보고) |

각 detail plan에 *해당 deferred item을 어떻게 풀었는지* 기록 → 진행 중 잃지 않음.

## 작성 흐름

```
Concept lock
    ↓
S0 detail 작성 → S0 실행 → 학습 기록
    ↓
S1 detail 작성 (S0 학습 반영) → S1 실행 → 학습 기록
    ↓
S1.5 detail 작성 (S1 학습 반영) → S1.5 실행 → 학습 기록
    ↓
...
    ↓
S6 detail 작성 → S6 실행 → v1.0 dev-complete 또는 Layer 3 진입
```

**원칙**: 한 detail plan을 *2개 이상 앞서 짜지 않음*. 짜면 prose-shape 함정 재현.

## Concept vs Detail 차이 — 한 번 더 확실히

| 차원 | Concept (v1.0-concept.md) | Detail (v1.0-detail-S*.md) |
|------|---------------------------|---------------------------|
| 작성 시점 | 한 번, 사용자 컨펌 후 lock | 각 step 진입 직전 |
| 길이 | 한 페이지 | step 크기에 따라 |
| 내용 | 방향 / 원칙 / 게이트 골격 | 5-10 단계 procedure / 입출력 / artifact-level gate 문구 |
| 변경 | 방향 자체 바뀔 때만 | 학습마다 자유롭게 |
| 검증 | 외부 검증 (Codex/Evaluator) | 작성 직후 self-check (체크리스트) |
| 누가 읽음 | 사용자 + Claude (매 세션 시작 시) | 해당 step 실행 Claude만 |

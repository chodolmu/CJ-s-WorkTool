## CR-1 — orphan flag: `/gmk-validate --rebaseline` 미정의

**위치**: `skills/gmk-regression/SKILL.md:219, 242`

```
Consider /gmk-validate <m> --rebaseline to update each baseline against current personas first.
Doesn't auto-rebaseline. That's a deliberate /gmk-validate <m> --rebaseline call by the user.
```

**증거**: `gmk-validate/SKILL.md`를 grep — `rebaseline` 0 hit.

**영향**: 사용자가 regression 후 안내를 따라 `gmk-validate <m> --rebaseline`을 호출하면 → 정의되지 않은 플래그. gmk-validate가 무시하거나 에러. *사용자가 막힘*.

**심각도**: ★★ — drift 안내가 실제로는 dead reference. flow break.

**제안 처리**: 둘 중 하나
- (a) `gmk-validate`에 `--rebaseline` 플래그 추가 정의 (현재 trial을 새 baseline으로 덮어쓰기)
- (b) `gmk-regression` 본문 정정: rebaseline은 *수동 절차* (validate 새로 돌리고 결과 복사)로 명시

## CR-3 — Shader template "Wave D" misleading 카피

**위치**: `templates/prototype-shader.html:19-32`, `skills/gmk-prototype/SKILL.md:90, 207`

```
WAVE D STUB NOTE: This shader template is a v0.2 STUB.
Doesn't ship the full shader template in v0.2. Stub + bot-INCONCLUSIVE messaging
only; full template lands in Wave D.
```

**증거**: 현재 shader template은 의도된 minimal stub(observation 805 확인). 의도는 정상.

**영향**: "Wave D"는 v0.2 backlog의 Wave D를 가리키는데, v0.3는 다른 Wave 분해를 했음. 카피가 *해소된 적 없는 약속*처럼 읽힘 — 신규 사용자가 "다음 Wave에 더 좋은 게 온다"고 오해.

**심각도**: ★ — 의미 결함 아니고 카피 stale. v0.3 Rule 11이 shader 검증 경로를 명시했으므로 stub 정책은 *정착됨*.

**제안 처리**: 본문에서 "Wave D" 표현 → "intentionally minimal stub; full WebGL2 work is opt-in user task"로 교체. shader template 헤더도 동일.

## CR-6 — `gmk-prototype` `--bot-only` 플래그의 effect 모호

**위치**: `skills/gmk-prototype/SKILL.md:184`

```
If the user invoked Step 3 with --bot-only (skipping the self-test row),
the entry's hypothesis still lists a placeholder self-test row with
verdict: "PASS" deferred to the user.
```

**영향**: `--bot-only`는 self-test row를 *진짜 생략*하지 않고 *placeholder PASS*를 적음. 이 placeholder가 schema gate를 어떻게 통과하는지 명확치 않음 (검증 시 PASS로 인정? 사용자가 따로 PASS/FAIL 다시 적어야?). flow 미정.

**심각도**: ★★ — flag 의미가 모호하면 사용자가 잘못 쓰기 쉽다.

**제안 처리**: `--bot-only`의 정확한 의미 명문화:
- placeholder PASS는 *사용자가 self-test 후 덮어쓰기 전까지의 임시 상태*인지
- 아니면 *진짜 self-test 면제*인지
+ 후속 SKILL (gmk-validate / gmk-self-test)이 placeholder PASS를 어떻게 다루는지 명시

## CR-7 — Agent 4명의 invocation 경로 일관성 부족

**위치**: 4 agent SKILL reference 분포 (Path A 검증에서 확인)
- systems-designer: 6 SKILL 언급
- feel-engineer: 6
- economy-balancer: 6
- playtest-analyst: 5

각 SKILL에서 라우팅 조건이 *개별 정의*됨. **공통 트리거 규약 없음** — 어떤 SKILL은 "Recommend `@agent` next" 출력, 다른 SKILL은 "Spawn agent inline" 식. v0.3 Wave A가 wiring을 추가하긴 했으나 *형식*은 SKILL마다 다름.

**증거**: gmk-design-system Step 9는 "the user runs `@systems-designer <milestone-id>` themselves"; gmk-validate는 "the user reads the suggestion, then runs `@playtest-analyst <id>`"; gmk-port stage 4는 다른 형식.

**심각도**: ★★ — agent routing이 v0.3의 핵심 wiring이었는데 형식 일관성 부족이면 사용자가 매번 다른 패턴 읽음.

**제안 처리**: 공통 agent-routing block 템플릿 작성 → 모든 SKILL이 같은 형식으로 추천 출력. 예:
```
Next agent (optional):
  @<agent-name> <milestone-id>   — <one-line reason>
```

## CR-8 — `gmk-loop` lock 파일 경로의 OS 가정

**위치**: `skills/gmk-loop/SKILL.md:59`

```
.gamemaker-kit/.loop.lock
```

**영향**: 잠금 파일 경로 hardcoded. Windows에서 `.`로 시작하는 파일이 OS에 문제 없지만 일부 백업/sync 도구가 무시. macOS/Linux는 hidden. *교차 OS 정책 명시 안 됨*.

또한 lock leak 처리 (line 153): "started_at; if > 1 hour and user manually deletes" — *자동 만료 없음*. 1시간 후에도 lock 있으면 사용자가 손으로 지움. 의도일 수 있으나 신규 사용자 함정.

**심각도**: ★ — 미세한 운용 결함. lock 자동 만료를 추가하면 UX 개선.

**제안 처리**: lock 파일에 `started_at` + 60min 이후 자동 expire 정책. 또는 명시적으로 "수동 정리만" 라인을 더 강하게.

## CR-9 — Plugin meta 파일이 SKILL 인벤토리와 단방향 sync

**위치**: `.claude-plugin/marketplace.json` + `plugin.json`

**관찰**: 이 두 파일은 사용자가 plugin install/list할 때 표시되는 SKILL 인벤토리를 담음. 매 SKILL 추가/제거마다 사람이 수동 동기화. v0.3 Wave E에서 dev-complete SKILL 추가 시 사람이 손으로 marketplace 갱신.

**영향**: drift 가능. v0.4에서 SKILL 추가/제거하면 또 손으로 동기화. 의도된 결함은 아니지만 자동화 안 됨.

**심각도**: ★ — 운용 결함. validation script로 자동화 가능.

**제안 처리**: `scripts/check-plugin-meta.sh` 같은 게이트 추가 — `skills/` 디렉토리 vs `marketplace.json` SKILL 목록 diff. CI 또는 pre-commit hook으로 강제.

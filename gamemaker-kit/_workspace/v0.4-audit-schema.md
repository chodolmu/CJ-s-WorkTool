**제안 처리** (둘 중 하나):
- (a) `gmk-graveyard-mine` / `gmk-trial-history` 등 mining SKILL을 v0.4에서 추가 (write-only를 *read-also*로 전환)

## SC-2 — Example 파일과 SKILL schema의 drift

**위치**: `_workspace/examples/milestones-example.json:220`

```
"_kill_reason": "Mechanic graft violates pillar..."
```

**비교**: gmk-kill-milestone SKILL.md는 `kill_reason` (underscore 없음) 필드를 정의. example만 `_kill_reason`. 

**가능 의미**:
- (a) example 작성 당시 *주석 목적*으로 underscore-prefix 사용 (실제 schema는 `kill_reason`). 의도된 차이.
- (b) schema rename이 example에 반영 안 됨 (drift).

**영향**: 신규 사용자가 example을 copy-paste → SKILL이 `kill_reason`을 못 찾음 (실제로는 `_kill_reason`). v0.3 Wave C가 structure.md drift는 해소했지만 *example file은 audit 안 함*.

**심각도**: ★ — 데이터 손실 없음 (kill을 SKILL로 호출하면 정상 필드 작성).

**제안**: example.json에서 `_kill_reason` → `kill_reason`으로 정정.

## SC-4 — `pillars.json` schema가 example로만 정의됨, 명시적 schema 문서 없음

**관찰**: `_workspace/examples/`에 milestones-example.json만 있고 pillars-example.json은 *없음*. pillars 스키마는 gmk-init SKILL.md 본문 + 다른 SKILL의 read 부분에서 *암묵적으로* 정의됨.

**영향**:
- pillars.json 필드 (`pillars[]`, `anti_examples[]`, `supported_genres_check`, `skipped: true` 등)가 *single source of truth* 없이 SKILL 간 산재.
- 사용자가 pillars.json을 hand-edit하려 할 때 *유효 schema 참조*가 없음.

**심각도**: ★★ — milestones.json은 example.json이 ground truth 역할, pillars.json은 없음. 불대칭.

**제안**: `_workspace/examples/pillars-example.json` 추가. v0.3 Wave C structure.md 갱신 시 빠진 부분.

## SC-5 — Port checklist의 schema 부재

**위치**: `.gamemaker-kit/port-checklists/<m>.md` — markdown 파일. SKILL.md (gmk-port) 본문에 *예시*는 있으나 *명시 schema* 없음.

**Read 추적**: `port-checklist` 또는 `checklist` 본문을 다른 SKILL이 read하는 곳:
- gmk-dev-complete C5: `forced: true on any gate` — JSON field만 읽음, markdown 안 읽음
- gmk-status, gmk-loop: 파일 *존재만* 확인

**영향**: port checklist가 *사람이 읽는 마크다운*이라 자유 형식 — drift 가능. v0.3 dev-complete가 `forced` 체크하는데 checklist 본문은 안 봄. OK이지만 schema-less.

**심각도**: ★ — 의도된 자유 형식일 수 있음.

**제안**: 본문 자체는 자유지만 *상단 frontmatter*에 필수 키 정의 검토 (`milestone_id`, `engine`, `stages_complete` 등).

## SC-6 — `prototype` 필드의 path 정규화 미정

**위치**: 모든 milestone에 `"prototype": "prototypes/<name>.html"`. relative path.

**관찰**:
- gmk-validate, gmk-self-test가 `prototype` 필드를 read.
- *어디 기준* relative인지 명시 없음 (project root? .gamemaker-kit?).
- 사용자가 `prototype: "C:\\GameMaking\\.../prototypes/m1.html"` 같은 absolute path를 쓰면? 행동 미정.

**심각도**: ★ — 실제 사용자 대부분 relative `prototypes/` 패턴 따라가지만 명시 부재.

**제안**: structure.md에 *path convention* 1 줄 명시.

## SC-8 — `merge_gate.touched_files` 형식 미정

**위치**: SKILL 본문 (gmk-merge-gate line 203):
```
touched_files is the asset-conflict diff list (without prototypes/etc.).
Future merge gates of other milestones use this list when computing Check 2.
```

**Read 추적**: `touched_files` 다른 SKILL grep:
- gmk-merge-gate가 write + read (다음 milestone의 Check 2).

**관찰**: write/read 모두 같은 SKILL → *closed loop*. OK이지만 *array of relative paths*인지 *object*인지 example.json에는 *빈 배열* (`[]`)만 있어 형식 불명.

**심각도**: ★ — 의도는 작동 가능, 명시 부족.

**제안**: example.json `merge_gate.touched_files`에 *한 개* 실제 path 예시 추가.

## SC-9 — Schema versioning 부재

**관찰**: milestones.json의 *최상위* 또는 milestone 단위에 `schema_version` 필드 없음. v0.1 → v0.2 → v0.3 변화 (필드 추가) 동안 *현재 버전 추적 메커니즘 없음*.

**영향**: v0.4가 *breaking schema change*를 도입하면 사용자가 어떤 버전의 milestones.json을 가졌는지 알 방법 부재. v0.3는 backward-compat 약속이지만 v0.4부터는?

**심각도**: ★★ — 미래 breaking change 시 큰 문제.

**제안**: 최상위 (`milestones.json` 루트)에 `kit_version: "0.3.0"` 추가. v0.4에서 schema 변화 시 migration SKILL 또는 자동 upgrade 로직 base.

## 3 CRITICAL gaps (Codex-verified)

### Gap 1 — Screenshot-grounded validation
**Status**: v1.0 `/gmk-validate` measures action/coverage/strategy *but does not look at the screen*. Visual regressions slip through (clipping, frozen sprite, missing asset, frozen animation).

**Prior art**: [`htdt/godogen`](https://github.com/htdt/godogen) (3.3k stars, Codex 5/5 substance)
- Loop: Plan → Code → Assets → Run → **Screenshot validation** → Fix
- README verbatim: *"the agent captures gameplay screenshots and judges progress against visible defects—clipping, incorrect scaling, frozen animations, missing assets—ensuring what appears on screen matches intent."*

**Codex constraint**: *"루프 설계 패턴만 베껴라. Godot/Bevy/Babylon 전제를 통째로 도입하면 비용 과잉."*

**Maps to**: S4 detail (`/gmk-port` metric-diff stage add-on, Phase-2 engine port). NOT for HTML prototype path (over-cost vs. value).

**P1 compliance**: screenshot-defect detection must produce a **machine-parseable verdict** (pass/fail + defect-category enum), not a prose description.

### Gap 2 — Gameplay invariant catalog (D-013 defense)
**Status**: v1.0 `/gmk-validate` runs persona-mix and computes metrics, but has no *explicit invariant list* that machine-rejects degenerate strategies. D-013 (degenerate hypothesis surfaced in v0.10 dogfood) would have been caught by an invariant check.

**Prior art**: [`abagames/agentic-gamedev-skills`](https://github.com/abagames/agentic-gamedev-skills) (Codex 4/5)
- README verbatim: *"prevent idle, hold-only, mashing, or repeated scoring dominance"*
- README verbatim: *"balance is evaluated through telemetry by comparing monotonous play policies against exploratory or intended-skill policies."*

**Codex constraint**: *"stars 4, commits 7 = 실험 샘플 수준. 아이디어 참고용으로만 처리."* — lift the invariant *list*, not the codebase.

**Maps to**: S2 detail (`/gmk-validate` upgrade). The invariant set becomes a pass/fail boolean alongside existing metrics:
- `no_idle_dominance` — non-action policy must not achieve top-quartile score
- `no_hold_only` — single-button-held policy must not achieve top-quartile score
- `no_mashing_dominance` — random-mash policy must not achieve top-quartile score
- `no_repeated_scoring` — single repeating action sequence must not achieve top-quartile score

**P1 compliance**: each invariant must be evaluated as `pass | fail | not_applicable` enum, written to `aggregated.json` alongside `dominant_strategy_ratio`.

**Codex constraint**: *"게임 자산이 아니라 Codex↔Claude Code 브리지다. slash-command UX와 background review/result 흐름만 참고."*

**Maps to**: S6 detail (`/gmk-merge-gate`) and S5 detail (before `/gmk-port`). Adversarial step is *opt-in per-milestone* (cost vs. value: only for milestones flagged "high cost-to-revert").

**P8 compliance**: adversarial review output must be a resumable artifact (`.gamemaker-kit/adversarial-reviews/<milestone>.md`), not in-conversation prose, so a session-cut session can re-enter mid-review.

## 2 NEW CRITICAL gaps (round-2 research, Codex-flagged categories)

Round-2 covered 4 categories Codex flagged as missed (GDD auto-gen / synthetic playtester / sound agent / VLM intent). Of those 4, 2 surfaced critical prior art.

### Gap 4 — Synthetic UX playtester (1st-pass filter before user self-test)
**Status**: v1.0 `/gmk-self-test` requires user 1-2h per milestone. No automated 1st-pass filter exists between `/gmk-validate` (statistical) and user self-test (subjective). User attention is the bottleneck (P8 — sessions are 1-2h/day total).

**Prior art**:
- [`Tencent/PlayCoder`](https://github.com/Tencent/PlayCoder) (35★, FSE'2026 paper) — PlayTester subsystem: **Visual Observer (screenshot) + Action Executor (GUI ops) + Test Manager (VLM plans next step)**. README verbatim: *"Uses VLM to analyze screenshots and plan test strategies."* Detects *"silent failures"* — behavior bugs without crashes.
- [`fagemx/gstack-game`](https://github.com/fagemx/gstack-game) `/player-experience` (33★) — 7 personas × 4D model (profile/stance/behavior/influence) + emotion model + repeat-play sim. Emits "Aha moments" / "boredom detection" 1st-person walkthrough.

**Why critical for v1.0**: signal *kind* is different from Gap 1 (visual defects) and Gap 2 (gameplay invariants). PlayCoder catches *navigational dead-ends, UX confusion, stuck-state-without-crash* — exactly what bot-trial statistics miss. gstack `/player-experience` is a softer persona-walkthrough variant.

**Codex constraint not yet sought** — but PlayCoder is academic (FSE'2026), substance is documented. gstack persona-spec is paper-light.

**Maps to**: S3 detail (`/gmk-validate` upgrade) — add as *UX layer* alongside the existing statistical layer. Output: `aggregated.json` gets new `ux_filter` block (`silent_failures: int`, `dead_ends: int`, `boredom_signals: int`).

**P1 compliance**: VLM verdicts must reduce to enums (`pass | fail | inconclusive`) per requirement, not prose.

### Gap 5 — Visual intent alignment (godogen-defect detection upgrade)
**Status**: Gap 1 (godogen) detects *visible defects* (clipping, missing asset). It does not judge *"does the screen match the design intent."* A clean-looking screen can still violate the milestone hypothesis.

**Prior art**: [`leigest519/OpenGame`](https://github.com/leigest519/OpenGame) (OpenGame-Bench, arXiv [2604.18394](https://arxiv.org/abs/2604.18394), 2026-04 release)
- 3-axis evaluation: **Build Health / Visual Usability / Intent Alignment**
- README verbatim: *"derives a weighted pass rate from per-requirement verdicts produced by a VLM judge against a structured requirement specification automatically compiled from the original prompt."*

**Why critical for v1.0**: maps almost 1:1 to our setup. `pillars.json` + milestone hypothesis ARE the "structured requirement spec." The VLM-judge-per-requirement pattern produces a machine-parseable per-pillar pass rate.

**Maps to**: S3 detail (`/gmk-validate` Intent Alignment row) + S5 detail (`/gmk-port` re-validation — Intent must survive engine port).

**P1 compliance**: weighted pass rate is numeric, per-requirement verdicts are enum — strictly machine-parseable.

**Relationship to Gap 1**: godogen detects *"what's broken on screen."* OpenGame detects *"what's on screen vs what was supposed to be there."* Both wanted, but Gap 5 is the stronger signal — adopt Gap 5 first.

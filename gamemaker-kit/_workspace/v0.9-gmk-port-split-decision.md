## Decision: KEEP at 684 lines

**Rationale**:

1. **No compliance gate exists**. Rule 2 (300/600 line caps) targets `templates/prototype-*.html` mechanic prototypes, *not* SKILL.md reference docs. `gmk-prototype-rules:58` calibrates the caps for prototype mental-model load (the user reading code), not doc length (the kit running a procedure). The v0.8 commit message explicitly states this. There is no doc-cap rule today and adding one is out of scope for v0.9 (see HANDOFF Tier 2 non-targets).

2. **The 6 stages are operationally one flow**. `gmk-port` runs Stages 1-6 sequentially against the same artifact (the HTML prototype being ported). Splitting at Stage 5/6 would force the user to remember which sub-skill to call when ("did I finish stage 5? do I now run /gmk-port-rerun?") — UX cost without procedural benefit. The kit's `/gmk-loop` dispatches the whole flow as one unit.

3. **Stage 6 (L396-412, 17 lines) is too small to extract**. The natural split candidate by section size is `## What the bot validated` (L443-601, 159 lines), but that section is a per-mechanic *reference catalog* — it documents which port-risk patterns are caught at Stages 3-4 vs. need human re-tuning. Extracting it to a separate `gmk-port-translation-rules.md` would (a) duplicate the Rule-14-style cross-reference burden and (b) hide the catalog from the user actively reading the port flow.

4. **No agent or user reports difficulty navigating the file**. Splits are warranted when (a) the doc fails a compliance gate, (b) a user/agent flow needs to call sub-flows independently, or (c) the file has structural smell (orphan sections, contradictions). None of those apply here.

5. **Compared to `gmk-prototype-rules` (570 lines, growing)**, `gmk-port` is in the same readability tier — both are top-of-tail-distribution but operationally cohesive. No splitting case applies here either, and no one is proposing it for prototype-rules.

**Counter-argument considered**: "684 lines is hard to skim." Mitigation: the file already has clear `^## ` section headers (9 sections) and the kit's smart_outline / glob tooling surfaces them. A reader looking for Stage 3 doesn't read L43-395 linearly; they jump to the Stage 3 sub-heading.

## Triggers that would re-open this decision

This decision is good for v0.9 and v1.0. Re-evaluate if **any** of the following happens:

| Trigger | Reason to re-split |
|---|---|
| `gmk-port` grows beyond 800 lines | Past the comfort threshold even for reference docs |
| A new SKILL needs to call into a subset of port (e.g., "re-run Stages 3-4 only" as a standalone skill) | Operational split becomes warranted |
| `gmk-loop` adds a per-stage hook that needs each Stage as a separate dispatchable unit | Same |
| User reports inability to find specific content via the section headers | Structural smell |
| A future Rule for SKILL.md max length is introduced | Compliance gate (would also affect prototype-rules) |

If none of those happen, the decision stands.

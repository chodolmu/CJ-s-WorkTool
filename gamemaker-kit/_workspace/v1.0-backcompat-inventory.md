# v1.0 — backward-compatibility inventory (v0.x guarantees that v1.0 may break)

**Date**: 2026-05-18 (21:28 KST)
**Cycle**: v0.9 — written as T2-C (M-NEW-3) per Protocol 1 §3
**Purpose**: enumerate every backward-compat guarantee made across v0.1–v0.9 so the v1.0 MAJOR bump can make break-or-keep decisions **deliberately**, not by accident.
**Status**: informational. v0.9 itself breaks nothing — v1.0 is the next opportunity to break things, and this inventory is the target list.
**Author scope**: best-effort scan of CHANGELOG.md, Rule 16, structure.md, prototype-rules. Not exhaustive — v1.0 work-start Protocol 1 should re-grep against this list.

---

## Why this exists

Every v0.x sub-release has been additive-only by promise (Rule 16 row 2, CHANGELOG L490, structure.md:107/552). The aggregate of those promises is a *backward-compat surface* — a list of behaviors the kit has implicitly committed to preserving. When v1.0 ships, the MAJOR bump *permits* breaking these (per SemVer + Rule 16's own "if a future MAJOR bump breaks schema compatibility, this rule will be revised"). Without an inventory, v1.0 may break things accidentally (regression) or fail to break things deliberately (carries v0.x cruft into v1.x indefinitely).

## Inventory

### Category 1 — Schema additive-only guarantee (Rule 16 row 2)

**Guarantee**: every v0.X schema addition is optional. v0.1 milestones.json and pillars.json still load against v0.X readers.

**Sources**:
- `skills/gmk-prototype-rules/SKILL.md:461` Rule 16 row 2 — "`kit_version` ≤ current → schema is additive-only across sub-releases, so older files validate as a subset."
- `CHANGELOG.md:490` v0.2 — "Schemas (additive only — v0.1 milestones.json still loads)"
- `_workspace/structure.md:107` — "Backward compat: v0.1 entries (no `tasks[]`, no `self_test`, etc.) MUST still validate"
- `_workspace/structure.md:552` — "every v0.2 schema addition is *optional*. A v0.1 milestone with only the seven original fields still validates."
- `CONCEPT.md:264` — "All v0.2 fields are **additive**; v0.1 milestones.json still loads."

**v1.0 break candidates**:
- **Drop the v0.1 fallback path** for fields like `tasks[]`, `self_test`, `validation`. v1.0 readers could *require* the v0.4+ shape and refuse files older than `kit_version: "0.4.0"`. Trade-off: simpler reader code vs. losing the ability to open a v0.1 project from 2026-05-11 era.
- **Make `kit_version` mandatory** (currently Rule 16 row 1 treats absent as `"0.3.0"`). v1.0 readers could refuse on absent. Affects: only pre-v0.4 files (kit started writing the field at v0.4).
- **Make `pillars[].kind` mandatory** (currently Rule 17 falls back to free-text on absent). v1.0 could require the field. Affects: pre-v0.4 pillars.json (kind introduced at v0.4).

### Category 2 — Deprecated-field forgiveness ("no data loss" promise)

**Guarantee**: deprecated fields remain readable forever. The kit ignores them silently rather than refusing.

**Sources**:
- `CHANGELOG.md:307` (v0.4 §) — "v0.4 skills no longer write these. v0.3 files containing them validate; skills ignore them. **No data loss**"
- `CHANGELOG.md:250` (v0.5 §) — "No data loss. v0.4 files with deprecated fields still read as-is."
- `CHANGELOG.md:96` (v0.7 Rule 16) — "Warn-only by design — refusing on newer-version files would lock users out of their own data after any plugin upgrade/downgrade. Preserves v0.4's 'no data loss' promise."
- `CHANGELOG.md:20` (v0.8 Rule 17) — "Same 'no data loss' promise as Rule 16."
- `_workspace/structure.md:563` "v0.4 deprecated fields (read-only, not written)"

**The 9 deprecated fields** (CHANGELOG L305-307, applied half-way until v0.5):
- `kill_history[]` (gmk-kill-milestone)
- `self_test.sessions[]` body + `coded_themes` (gmk-self-test)
- `validation_history[]` (gmk-validate)
- 6 others enumerated in v0.3 schema docs

**v1.0 break candidates**:
- **Stop silently ignoring deprecated fields** — v1.0 readers could warn-and-strip (one-time migration) or even refuse. Trade-off: cleaner v1.x file shape vs. breaking the "no data loss" promise that 4 consecutive releases (v0.4–v0.7) have reinforced.
- **Auto-strip deprecated fields on next write** — middle ground; v1.0 reads them, doesn't preserve them on write. Documented under SemVer-MAJOR-permits-this.
- **Drop the legacy `measured_by.kind: 'human'` → `'self-test'` migration** (CONCEPT.md:264). v1.0 could refuse `'human'` outright (it's been auto-migrating since v0.2 — long deprecation window).

### Category 3 — Bot hook API additivity (`_gmkApiVersion: 1`)

**Guarantee**: `_gmkApiVersion: 1` is the API version. New optional callbacks added across sub-releases. Prototypes with only the 5 required callbacks remain functional.

**Sources**:
- `CHANGELOG.md:431` v0.2 — "_bot_hook_lib.js — no API changes (still _gmkApiVersion: 1, additive)."
- `CHANGELOG.md:477` v0.X — "four optional persona callbacks (stateSignature, riskEstimate, progressEstimate, noveltyScore), _gmkPersonaCapabilities introspection, _gmkApiVersion: 1 retained (additive only)."
- `CHANGELOG.md:500` — "prototypes without the new callbacks still validate (hook surface returns null, persona falls back to random and the result records fallback_used)."
- `templates/_bot_hook_lib.js:80` — "additive. v0.1 prototypes with only the five required callbacks remain"
- `templates/prototype-shader.html:271-294` (verified in v0.8 Protocol 4) — explicit comment that `riskEstimate`/`noveltyScore` are intentionally omitted with rationale.

**v1.0 break candidates**:
- **Bump to `_gmkApiVersion: 2`** — v1.0 could require new mandatory callbacks (e.g., make `stateSignature` required since most personas already use it). v0.X prototypes with only 5 callbacks would refuse. Trade-off: cleaner bot logic vs. forcing every v0.X prototype to update.
- **Remove the `fallback_used` recording mechanism** (it exists only because old prototypes lack optional callbacks; if v1.0 makes the callbacks mandatory, the fallback path becomes unreachable and can be removed from gmk-validate's reporting).

### Category 4 — Pillar shape free-text fallback (Rule 17 row 2)

**Guarantee**: skills that route on pillar shape fall back to free-text classification if `kind` is absent (so user-authored pillars from before v0.8 still work).

**Sources**:
- `skills/gmk-prototype-rules/SKILL.md:494` Rule 17 row 2 — "Fall back to free-text classification on the pillar's name + description (the pre-v0.8 behavior)"

**v1.0 break candidates**:
- **Remove the free-text fallback** — v1.0 readers could refuse on absent `kind`. Same trade-off as Category 1 break: forces all pillars.json to declare `kind`, but cleaner shape-routing code (no free-text classification logic to maintain).

### Category 5 — Endpoint terminology (v0.5+ standardization)

**Guarantee**: documentation uses "checkpoint" / "release-readiness checkpoint" instead of "endpoint" for the dev-complete state (per v0.5 Check B rule, v0.8 promoted to FAIL).

**Sources**:
- `scripts/check-plugin-meta.sh:147` Check B — FAIL-level since v0.8
- `.endpoint-allowlist.txt` — 6 allowlisted intentional uses
- HANDOFF §"v0.6 → v0.7" — endpoint terminology audit history

**v1.0 break candidates**:
- **None expected** — this is a documentation convention, not a schema or API guarantee. v1.0 inherits Check B as-is. No break candidate here.

### Category 6 — `human:` → `self-test:` hypothesis row migration

**Guarantee**: `gmk-prototype-rules --check` warns once and migrates `human:` rows in hypothesis headers to `self-test:` (per `prototype-rules:537`).

**Sources**:
- `skills/gmk-prototype-rules/SKILL.md:537` violations table

**v1.0 break candidates**:
- **Stop the auto-migration** — v1.0 could refuse on `human:` rows entirely. Old hypothesis headers from v0.1-era prototypes would fail to parse. Long deprecation window (since v0.2) — break is defensible.

## What this inventory is NOT

- **Not a v1.0 work plan.** Each "break candidate" above is a *decision*, not a commitment. v1.0 work-start Protocol 1 will select which breaks to take and which to keep.
- **Not exhaustive.** Best-effort grep against CHANGELOG/Rule 16/Rule 17/structure.md/prototype-rules. The actual v1.0 Protocol 1 should re-grep for anything missed (analogous to F21 — author anchors on what they grepped first).
- **Not a CHANGELOG.** v1.0's eventual CHANGELOG entry will document *which* of these breaks were taken. This inventory is the menu, not the order.

## Open question for v1.0 work-start

The kit's `kit_version` Rule 16 currently says: *"If a future MAJOR-version bump (1.0.0+) breaks schema compatibility, this rule will be revised — but additive-only sub-releases (0.X.Y) are guaranteed not to break old files."*

This is permission to break, not an obligation. The Protocol 1 evaluator for v1.0 should answer: *which Category 1-6 breaks are worth the migration cost users will pay?* The default answer is "as few as possible" — every break costs users a migration step or refusal-on-old-data, and the kit's "no data loss" promise has been a meaningful trust anchor for 6 releases.

A reasonable v1.0 break set might be:
- Category 1 — require `kit_version` field (cheap; only affects pre-v0.4 files, which are unlikely to exist in the wild)
- Category 4 — require `pillars[].kind` (more aggressive; forces users to declare shape, but eliminates free-text inference maintenance)
- Category 6 — refuse `human:` rows (very long deprecation, defensible break)

The other categories (2 deprecated fields, 3 API bump, 5 endpoint, 1 schema additive) might stay v0.x-compatible. v1.0 doesn't have to break everything — it just *may*.

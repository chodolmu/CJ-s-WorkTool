# WorkTool v3 — 태스크 드리븐 아키텍처 전환 계획

> **Feature**: 프로젝트 전체 재설계 — 하네스/GSD 중심 → 태스크 분할 + 컨텍스트 관리 중심
> **Date**: 2026-04-06
> **Status**: Draft

---

## 1. 문제 정의

### 1.1 현재 구조의 근본 문제

현재 WorkTool은 **"어떤 에이전트가 어떤 순서로 일하느냐"**를 설계하는 데 집중한다.
하지만 실제 병목은 그게 아니다:

| 실제 병목 | 현재 해결 여부 |
|-----------|---------------|
| AI에게 한 번에 얼마만큼의 일을 시키느냐 (스코프) | ❌ 해결 안 됨 |
| AI가 맥락을 얼마나 정확히 이해하느냐 (컨텍스트) | ❌ 해결 안 됨 |
| 작업 실패 시 얼마나 빨리 복구하느냐 (피드백 루프) | △ 부분적 |
| 비개발자가 쉽게 사용할 수 있느냐 (접근성) | ❌ 기술 중심 UI |

Director → Planner → Generator → Evaluator 파이프라인이 아무리 화려해도,
Generator에게 "게임 전체를 만들어"라고 던지면 망한다.

### 1.2 핵심 인사이트

> AI를 잘 쓰는 방법은 **"잘게 쪼개서, 명확하게, 깨끗한 컨텍스트에서"** 시키는 것이다.

## 2. 새 컨셉: 태스크 드리븐 아키텍처

### 2.1 핵심 원칙 6가지

1. **Opus가 PM** — 프로젝트 분할, 의존성, 난이도 판정, 검증 방법 설계
2. **태스크 단위 실행** — 매번 깨끗한 컨텍스트에서 시작
3. **Handoff로 연결** — 태스크 간 맥락 전달, 전체를 다 읽을 필요 없음
4. **실행 방식은 태스크가 결정** — 단순하면 단독 에이전트, 복잡하면 하네스
5. **하네스는 수단** — 업무에서 필요가 생겨야만 투입, 하네스를 위한 업무를 만들지 않음
6. **사용자는 승인자** — 분할 확인, 중간 점검, 방향 결정만

### 2.2 작업 분할 계층

```
프로젝트 (Project)
  └─ 마일스톤 (Milestone) — 배포 가능한 단위
       └─ 스프린트 (Sprint) — 검증 가능한 단위
            └─ 태스크 (Task) — AI에게 시킬 수 있는 최소 단위
```

### 2.3 전체 흐름

```
┌──────────────────────────────────────────────────────────────────┐
```

## 3. 작업 분할 상세

### 3.1 Opus PM의 역할

Opus는 프로젝트의 **PM(프로젝트 매니저)**으로서 다음을 수행:

#### 입력
- SpecCard (Discovery에서 생성된 프로젝트 정의)

#### 출력: 작업 트리

```typescript
interface ProjectPlan {
  milestones: Milestone[];
}

interface Milestone {
  id: string;
  name: string;
  description: string;          // 이 마일스톤이 완료되면 뭐가 되는지
  sprints: Sprint[];
  validationStrategy: string;   // 마일스톤 완료 시 어떻게 검증하는지
}

interface Sprint {
  id: string;
  milestoneId: string;
  name: string;
  description: string;
  tasks: Task[];
  dependencies: string[];       // 선행 스프린트 ID
  validationStrategy: string;   // 스프린트 완료 시 어떻게 검증하는지
}

interface Task {
  id: string;
  sprintId: string;
  name: string;
  description: string;          // 무엇을 해야 하는지
  plan: string;                 // 어떻게 해야 하는지 (구체적 계획)
  dependencies: string[];       // 선행 태스크 ID
  difficulty: "easy" | "medium" | "hard";
  model: "haiku" | "sonnet" | "opus";
  executionMode: "single" | "harness";
  harnessId?: string;           // harness 모드일 때만
  validation: {
    auto: string[];             // 자동 검증 (build, typecheck, lint 등)
    manual?: string;            // 수동 확인 필요 시
  };
  estimatedFiles: string[];     // 변경 예상 파일 목록
}
```

#### 분할 원칙 (Opus에게 주입할 가이드라인)

1. **태스크 하나 = "한 파일~몇 파일 수준 변경"** — 너무 크면 쪼갠다
2. **태스크 하나 = 명확한 완료 조건** — "~하면 끝" 이 한 문장으로 정의 가능해야
3. **의존성은 최소화** — 병렬 실행 가능하게
4. **업무에서 필요할 때만 하네스** — 하네스를 위한 업무를 만들지 않는다
5. **난이도 판정 기준**:
   - easy (haiku): 보일러플레이트, 설정 파일, 단순 복사/이동
   - medium (sonnet): 일반적인 기능 구현, 버그 수정, 리팩토링
   - hard (opus): 아키텍처 설계, 복잡한 알고리즘, 다중 파일 연쇄 변경

### 3.2 의존성 관리

의존성은 두 시점에서 관리:

#### 계획 시점 (Opus PM)
```
태스크 A: DB 스키마 설계        (의존: 없음)
태스크 B: API 엔드포인트 구현   (의존: A)
태스크 C: 프론트엔드 폼        (의존: B)
```

#### 실행 시점 (Handoff 갱신)
태스크 A 완료 후 handoff에 기록:
```markdown
## 설계 결정
- DB는 SQLite 대신 PostgreSQL 채택 (이유: ...)
- users 테이블에 role 컬럼 추가

## 후속 태스크 영향
- 태스크 B: connection string 변경 필요
- 태스크 C: role 선택 UI 추가 필요
```

Opus가 스프린트 완료 시점에 이런 변경사항을 반영해 후속 태스크 계획을 갱신한다.

## 4. 컨텍스트 관리

### 4.1 왜 중요한가

AI의 컨텍스트가 길어지면:
- 초반 지시를 무시하기 시작
- 코드 스타일이 일관성을 잃음
- "대충 끝내기" 경향 증가

### 4.2 컨텍스트 전략

```
┌─ 태스크 시작 ─────────────────────────────────┐
│                                                │
│  주입되는 컨텍스트:                              │
│  1. 태스크 계획 (plan 필드)                     │
│  2. 직전 태스크의 handoff (관련된 것만)           │
│  3. 프로젝트 전체 구조 요약 (파일 트리 등)        │
│  4. 해당 태스크의 검증 조건                      │
│                                                │
│  주입되지 않는 것:                               │
│  - 전체 대화 히스토리                            │
│  - 다른 태스크의 상세 내용                       │
│  - 이전 세션의 전체 로그                         │
│                                                │
└─ 태스크 완료 → handoff 생성 → 컨텍스트 클리어 ──┘
```

### 4.3 Handoff 구조

```typescript
interface TaskHandoff {
  taskId: string;
  completedAt: string;
  summary: string;              // 무엇을 했는지 (1-3문장)
  filesChanged: string[];       // 변경된 파일 목록
  designDecisions: string[];    // 설계 결정 사항 (후속 태스크에 영향)
  knownIssues: string[];        // 알려진 문제점
  nextTaskNotes?: string;       // 다음 태스크에 전할 말
}
```

## 5. 모델 배치 전략

### 5.1 기본 배치

| 난이도 | 모델 | 용도 | 비용 비율 |
|--------|------|------|-----------|
| easy | Haiku | 보일러플레이트, 설정, 단순 작업 | 1x |
| medium | Sonnet | 일반 구현, 버그 수정 | ~5x |
| hard | Opus | 설계, 복잡한 로직, 아키텍처 | ~15x |

### 5.2 고정 배치

| 역할 | 모델 | 이유 |
|------|------|------|
| PM (작업 분할) | Opus | 가장 어렵고 중요한 작업 |
| Discovery (프로젝트 정의) | Opus | 사용자 의도 정확히 파악 필요 |
| 스프린트 검증 | Sonnet | 코드 리뷰 + 통합 확인 |
| 마일스톤 QA | Opus | 전체 품질 판단 |
| 태스크 실행 | 난이도별 | PM이 판정 |

### 5.3 비용 최적화 예시

```
프로젝트: 크롬 공룡게임 클론
  마일스톤 3개 × 스프린트 ~3개 × 태스크 ~4개 = ~36 태스크

  Opus (PM + Discovery + QA): 5회     → 75 단위
  Sonnet (중간 난이도 태스크): 20회     → 100 단위
  Haiku (쉬운 태스크): 11회            → 11 단위
  ─────────────────────────────────
  총 비용: ~186 단위

  vs. 전부 Opus로 실행: 36 × 15 = 540 단위
  → 약 65% 비용 절감
```

## 6. 실행 방식: 단독 vs 하네스

### 6.1 판단 기준

Opus PM이 태스크 생성 시 결정. **업무가 먼저, 하네스는 수단.**

```
태스크 도출 → "이걸 어떻게 실행하는 게 최선인가?" → 단독 or 하네스
```

절대로:
```
❌ "하네스가 있으니 하네스에 맞는 태스크를 만들자"
```

| 기준 | 단독 (single) | 하네스 (harness) |
|------|--------------|-----------------|
| 관점 수 | 하나의 관점으로 충분 | 여러 전문 관점 필요 |
| 예시 | "로그인 폼 만들기" | "게임 밸런싱 설계" |
| 교차 검증 | 불필요 | 에이전트 간 교차 검증 필요 |
| 산출물 | 코드 파일 | 설계문서 + 코드 + 검증보고서 |

### 6.2 하네스 실행 시

```
태스크: "게임 난이도 곡선 설계"
  executionMode: "harness"
  harnessId: "game-balance"
  
  → 하네스 내부:
    게임디자이너 → 밸런서 → 테스터 협업
    산출물: _workspace/ 에 파일 생성
  → 완료 후 handoff 생성 (일반 태스크와 동일)
```

## 7. 검증 체계

### 7.1 3단계 검증

| 단위 | 타이밍 | 내용 | 자동/수동 |
|------|--------|------|-----------|
| 태스크 | 매 태스크 완료 시 | 빌드, 타입체크, 린트 | 자동 |
| 스프린트 | 스프린트 완료 시 | 통합 테스트, 기능 확인, 코드 리뷰 | 자동 + 사용자 확인 |
| 마일스톤 | 마일스톤 완료 시 | 전체 QA, 요구사항 충족 확인 | Opus QA + 사용자 승인 |

### 7.2 검증 실패 시

```
태스크 검증 실패
  → 같은 태스크 재실행 (handoff에 실패 원인 추가)
  → 2회 실패 시 사용자에게 알림

스프린트 검증 실패  
  → Opus가 실패 원인 분석
  → 수정 태스크 추가 생성
  → 수정 태스크 실행 후 재검증

마일스톤 검증 실패
  → Opus가 전체 리뷰
  → 필요시 스프린트 추가
  → 사용자 확인 후 진행
```

```
└─────────────────────────────────────────┘
```

### 8.3 페이지 구성

| 페이지 | 역할 |
|--------|------|
| **Discovery** | 프로젝트 정의 (기존 유지, 간소화) |
| **프로젝트 트리** | 메인 화면. 마일스톤/스프린트/태스크 진행률 |
| **태스크 상세** | 계획, 로그, handoff, 검증 결과 |
| **설정** | 모델 API 키, 기본 설정 |

기존 대비 **삭제**:
- OrchestrationPage (파이프라인 시각화)
- HarnessPage (하네스 브라우저 — 태스크에 녹아듦)
- SchedulePage (캘린더/간트 — 트리 뷰로 대체)
- 에이전트 풀 UI (PM이 자동 판단)
